## [Unreleased]

### Added

- **Plant registry, part 2: data points and KPIs (preview, #219, [docs/PLANT.md](docs/PLANT.md#device-profiles-data-points-and-kpis), [ADR 0007 – Part 2](docs/adr/0007-plant-registry.md#part-2-data-points-and-kpis-070))**: what each asset's interfaces deliver and which KPIs are computed from it.
  - **Device profiles** (_Plant → Device profiles_, a catalogue of the installation): manufacturer, model, version, category and the **interfaces** – OPC UA, Modbus/TCP, MQTT, web, SMB, WebDAV, SFTP, FTP – with direction, default port, sign-in and the client they need, their **data point groups and data points** (data type after OPC UA IEC 62541 or IEC 61131-3, unit as a UCUM code, address, access, update rate, values, notes) and the files of a file-transfer interface. OPC UA NodeIds and Modbus addresses (table, address, count; the function code is shown) are checked on every save. A data point has its own page with the assets that deliver it and the KPI definitions that read it.
  - **KPI definitions** (_Plant → KPI definitions_, a catalogue): category, the ISO 22400-2 attributes (formula, unit, range, trend, timing, audience, production methodology), inputs (a profile's data points), parameters with type, default, range and aliases, result columns of kind _sum_, _ratio_ (numerator and denominator) or _ignore_ with their scope, the computation with its steps, identities and limits; the assets with an instance and those that could have one.
  - **On the asset page – Data and KPIs**: the device profile and controller firmware, per interface whether it is set up and its endpoint, data points that differ on this asset, where its data points are published (target system, path, name), its **KPI instances** (job, active, parameters, the dashboard or dataset with the result) and the KPIs it can have.
  - **Checks** (on the asset, the KPI definition, _Plant → Checks_ and in the import preview, never blocking): a KPI instance whose data point inputs the asset does not deliver (no or another profile, an interface not active, a data point it lacks), parameters outside the definition (unknown, twice, wrong type, out of range, required but missing), a ratio without its numerator or denominator.
  - **Explore data**: which assets deliver a data point (a text across every profile), which KPIs an asset can have; the asset list filters by profile and data point.
  - **YAML import and export** in format 1 with new optional keys `device_profiles`, `kpi_definitions` and `assignments` (also one per file), the same modes and preview; usual spellings of other tools (`OPC-UA`, `Modbus/TCP`, `float[]`, `kWh`) are read as their standard value. The JSON Schema is regenerated; files of 0.6.0 stay valid. Exports of the catalogues, one profile and one KPI definition.
  - **Rights**: everyone who sees the registry sees the catalogues (the Plant viewer too); designers and administrators manage them; assignments and KPI instances follow the asset's site. Lists, counts, search and checks leave out assets of sites the reader may not see. _Duplicate_ for profiles and KPI definitions; an asset's copy takes its profile, not its endpoints or KPI instances. Every change is audited.
  - **API**: internal routes `/api/plant/profiles`, `/api/plant/kpis`, `/api/plant/assets/:assetId/assignment`, `/api/plant/explore/points`, `/api/plant/checks`; read endpoints `/api/v1/plant/profiles[/{profileId}]`, `/api/v1/plant/kpis[/{kpiId}]`, `/api/v1/plant/assets/{assetId}/assignment` and the filters `profile`, `dataPoint` on `/api/v1/plant/assets`.
  - The demo adds three invented device profiles, two KPI definitions and the assignments of four assets (`examples/plant/brightwater-data-points.plant.yaml`), one with a check problem on purpose. Migration `plant-002-data-points` (additive: new tables only).
- **Database platforms: PostgreSQL, MariaDB/MySQL and SQL Server, read-only** ([docs/DATABASES.md](docs/DATABASES.md), [ADR 0008](docs/adr/0008-database-platforms.md), #203): Steward connects to databases directly for access reviews, account hygiene, monitor checks and datasets.
  - **Platform kind _database_** (presets _PostgreSQL_, _MariaDB / MySQL_ and _Microsoft SQL Server (read-only)_, group _Databases_ in the setup wizard) with pure-JavaScript drivers (`pg`, new: `mysql2`, `tedious`). The new tab _Database_ holds the connection – host, port, database, TLS (verify with an optional CA, encrypt only, off), the limits and the pool size – sealed and audited (`platform.database_changed`); user name and password are credentials. The **connection test** reports the read-only session, an account that can write and the catalog queries the account may not read.
  - **Process step _Query a database_** (`type: query`): Steward's **catalog queries** (`status`, `accounts`, `role-members`, `privileges`, `replication`, `tables` – the same columns for every DBMS, with generated `REVOKE` / lock statements quoted for it) or **own SQL** – one `SELECT` or `WITH … SELECT` with bound parameters (`$1`, `?`, `@p1`). Always read-only: a read-only transaction on PostgreSQL and MariaDB/MySQL, a transaction that is rolled back on SQL Server, plus a conservative statement check in the editor and on the server; a time, row and size limit per statement (the platform's limits are the ceiling). The result is stored like an HTTP answer (run reports, evidence, the editor's _Last run_ shows a table); dry runs query, test runs use the recorded response `POST /sql/<step id>`.
  - **Monitor check _Database_**: the connection, the replication lag, or the value of a read-only query against WARN and CRIT.
  - **MCP gateway**: off by default; when on, the tool `database_query` (read-only, the same checks, audited); changing statements are refused (`MCP_WRITES_NOT_AVAILABLE`).
  - **Templates** for every supported DBMS: _Database – Access review_ (four-eyes, generated `REVOKE` statements as a manual step, documented access changes), _Database – Account hygiene_, _Database – Table sizes_, the own-SQL example _PostgreSQL – Connections per database_, the dashboard _Databases_, a monitor example and the bundle _Databases_. The demo has the simulated platform _Shop database (demo)_ (canned catalog rows; it never reads Steward's own database).
  - The host:port of a database follows the outbound policy like Kafka and MQTT; connections are pooled per platform (at most 5, closed after 60 s idle, on any change of the platform and on shutdown). New internal route `PUT /api/platforms/:id/database`; `/api/v1` lists the check type `database`. No migration.
  - **Hardened before release** (security review): the statement check also reads quoted function names and refuses functions that run SQL given as text, MariaDB/MySQL optimizer hints `/*+ … */`, row locks (`FOR SHARE` …, SQL Server lock hints) and the T-SQL words that start another statement (also a second `SELECT` outside parentheses) – a best-effort extra layer, the read-only account stays the protection; refusals are shown translated in the editor. PostgreSQL connections release session advisory locks before they are reused; a MariaDB/MySQL statement stopped by the time limit is ended on the server with `KILL QUERY`; a platform may not point at Steward's own database server (`DB_OWN_DATABASE`); driver errors are masked in monitor results and run steps.
- **Plant registry in the public API: checks and export** (#219, [docs/PLANT.md](docs/PLANT.md#fetching-the-registry-from-other-tools)): two more read endpoints for other tools and backups.
  - `GET /api/v1/plant/checks` lists what _Plant → Checks_ shows – kind, English message, asset, site, KPI definition, job and details – for the assets the token owner may see and the KPI definitions; filters `site`, `asset`, `kpi` (the definition's own problems and those of its instances), `kind`; paginated like the other lists.
  - `GET /api/v1/plant/export` gives the registry in the import format, as the export in the web app: everything the token owner may see, one site, the catalogues (`part=catalogue`), one profile or KPI definition; YAML (default) or JSON (`format=json`). Sites the owner may not see and their assets are never in it; it imports back unchanged and is audited (`plant.exported`, with the token id).
  - While the module is off, the plant endpoints of the public API now say so in their `404` (before: "Plant registry not found").

### Fixed

- **Plant registry: deleting a device profile or KPI definition in use** no longer hints at assets the person may not see: when an asset of a hidden site has it, the answer is only that it is in use (`PLANT_PROFILE_IN_USE_HIDDEN`, `PLANT_KPI_IN_USE_HIDDEN`, without a count); who sees every asset that has it gets the count.
- **Plant registry pages: long identifiers** no longer break mid-word ("ProgramStatu / s"): paths, names, addresses and ids wrap after `/`, `.`, `_`, `:` and `;`; in the publications table of an asset and the table of assets that deliver a data point they stay whole and the table scrolls when they do not fit.

## [0.6.0] - 2026-11-05

Steward 0.6.0 brings **AI models through LLM gateways** and part 1 of the **plant registry**. The process step _Ask an AI model_ sends a saved question with context from earlier steps, datasets or run inputs to an LLM gateway (OpenAI Chat Completions and every OpenAI-compatible API, OpenAI Responses, Anthropic Messages, Bedrock Converse), with allowed data per gateway, input limits per call, token budgets per day and month, a usage log and the _AI usage_ dataset; answers are marked as AI-generated. The plant registry (opt-in, preview) keeps the factories of an enterprise in one place: sites with their ISA-95 hierarchy and buildings, assets, links to Steward's systems and applications, and YAML import and export with a published JSON Schema, including replacing an earlier import. Status viewers are now also refused by the public API and the MCP endpoint. The database migrations (`ai-001`, `ai-002`, `plant-001`) only add tables and a column.

### Added

- **AI models through an LLM gateway** ([docs/AI.md](docs/AI.md), #216): a process asks an AI model a predefined question with context from earlier steps, CheckMk and other platforms or datasets, and uses the answer in later steps – a report, a check message, an e-mail or Teams notification. The AI does not act on its own; there are no tool calls and no chat.
  - **Platform kind _LLM gateway_** (preset _LLM gateway (AI models)_, group _AI models_ in the setup wizard): a base URL and the usual sign-in types – an API key in any header (`x-api-key` by default, `api-key`, `Authorization`) or a bearer token. One gateway can serve several request formats, so **the format belongs to the model**: OpenAI Chat Completions (also every OpenAI-compatible API), OpenAI Responses, Anthropic Messages (with `anthropic-version`) and Bedrock Converse (model id in the path). No streaming, no vendor SDK: one small adapter per format.
  - **Models** on the new tab _AI models_: read from `GET /v1/models` or entered by hand, each with its format, an optional path, the context window, the most output (and input) per call, an optional price per 1,000 input and output tokens and the characters per token of the estimate. **Allowed data** says what the gateway may be sent – data of chosen platforms, datasets by key pattern, run inputs; nothing until someone allows it. It is checked on the values sent, whichever step wrote them: the run records where each variable's value comes from, and a computed value counts as carrying everything of its run. Both are part of the platform's sealed settings and audited (`platform.ai_changed`). The **connection test** lists the models and asks each one once.
  - **Process step _Ask an AI model_** (`type: ai`): instructions and a question as a template saved with the process – `{{ name }}` inserts a context source, nothing else is filled in at run time; context from earlier steps, datasets or inputs, each with a size limit and an optional expression; secrets and secret-looking values removed before sending; the answer as text, or as JSON checked against a JSON Schema in the step (`AI_ANSWER_INVALID` otherwise; no `pattern` keywords); a fixed model, temperature and output limit; an error output. Dry runs use a sample answer and test runs a recorded response – neither calls the model.
  - **AI-generated marking**: reports and check messages (in-app, e-mail, Teams, webhook) that carry an answer say so and name the model; an approval with four-eyes before such a message leaves Steward uses the existing user tasks.
  - **Limits**: the input is estimated **before** sending (characters / 3.5, plus overhead; no tokenizer) and refused above the step's or the model's limit (`AI_INPUT_TOO_LARGE`), without a call. **Budgets** of tokens per day and month (UTC) for the installation, a gateway and a process (including its sub-processes): a call whose estimated input plus its most output no longer fits is refused before it is sent (`AI_BUDGET_EXHAUSTED`); the worst case is reserved in the same transaction, so parallel steps cannot overspend. A notification (event _AI budget_) goes out at 80 % and when a budget is used up. Raising a budget is audited (`ai.budget_changed`) and needs a step-up – the new control point `ai.budget` of the assurance policy (on by default). Token counts come from each format's usage fields.
  - **Reporting**: a usage log per call (time, process, run, step, gateway, model, format, tokens, duration, result, fingerprints of the prompt and the input – no content), the tab _AI usage_ on the gateway page (budgets, use today and this month, top processes and models, budgets of single processes, the latest calls), the built-in dataset _AI usage_ (`ai.usage`) with the dashboard template _AI usage_, the report section _AI usage_ for a monthly report schedule, and audit entries for refused calls (`ai.call_refused`).
  - **Demo and tests**: a simulated multi-format LLM gateway (`/mock/llm`, one model per format) as the demo platform _LLM gateway (demo)_, and the example process _CheckMk – AI summary of the trends_ (JSON answer, four-eyes approval, report and check).
  - New: the setting `SM_AI_USAGE_RETENTION_DAYS` (default 400 days), the background job `ai-usage`, the database migrations `ai-001-usage-and-budgets` (additive: tables `ai_usage`, `ai_budgets`, `ai_budget_notices`) and `ai-002-usage-parent-processes` (additive: column `ai_usage.parent_process_ids`), and the internal routes `PUT /api/platforms/:id/ai`, `POST /api/platforms/:id/ai/discover`, `GET /api/platforms/:id/ai/usage`, `GET`/`PUT /api/ai/budgets` and `GET /api/ai/usage`.
- **Plant registry, part 1 (preview, opt-in module, #217/#218, [docs/PLANT.md](docs/PLANT.md), [ADR 0007](docs/adr/0007-plant-registry.md))**: the factories of the enterprise in one place – off by default; turned off, nothing of it shows and its routes answer 404.
  - **Settings → Modules → Plant registry**: the switch, the enterprise's name, own display names per record type and language (_Machine_ instead of _Asset_) and own fields per record type, checked on every save and import. The sidebar gets the area **Plant** (_Sites_, _Assets_, _Import_).
  - **Sites** with code, translated names, position (a link to OpenStreetMap), contacts, external references (system, id, link) and own fields; their hierarchy after **ISA-95 / IEC 62264** – areas, work centers, work units, with an optional ISA-95 type and domain – and a separate axis of **buildings** (halls, floors, outdoor areas; IEC 81346: function and location apart), where the innermost building of a node wins.
  - **Assets** with a stable id, manufacturer, model, status, location (the innermost place decides, the levels above follow; an optional own building), the equipment they are part of (same site, no cycles) and their parts, taxonomy, tags, lifecycle, capabilities, an image (PNG, JPEG or WebP) and external references; the list filters by site, place, domain, status and tag. Assets can be duplicated (without their external references).
  - **Links**: sites and assets are link kinds – documents, records, tickets, services and applications name them, an asset names the systems, applications and platforms it uses (shown on the system page under _Linked from_). A reader sees only targets in sites they may see.
  - **YAML import and export** in a versioned format with a published **JSON Schema 2020-12** (`docs/plant/plant-registry-1.schema.json`): one file per site, assets apart or a whole tree, several files at once; a **preview** of what is added, changed and removed; the modes _add only_, _add and update_ and _replace an earlier import_ (missing records removed, or kept and marked _not in source_); stable ids; problems with the place in the file; limits like the other YAML importers; every import audited with its counts and the files' SHA-256. The export imports back unchanged.
  - **Permissions per site**: role defaults (everyone who works in Steward sees a site, designers manage it), an access list (_view_, _manage_; adding entries asks for a step-up), owning teams, and the new role **Plant viewer** (`plant`) that sees only the registry (the server refuses everything else to a user with no other working role; the web app shows the Plant area and the profile). Nothing of it is on status pages.
  - **API**: the internal routes under `/api/plant/…` and read endpoints `/api/v1/plant/sites[/{siteId}]` and `/api/v1/plant/assets[/{assetId}]` (`ref=system:id` finds an asset by another tool's id).
  - The demo loads an invented enterprise with two sites (`examples/plant/brightwater.plant.yaml`) when the module is turned on. Migration `plant-001-registry` (additive: new tables only).

### Fixed

- **Status viewers and API tokens**: a status viewer is refused by the public API (`/api/v1`) and the MCP endpoint, also with a token made before the account became a status viewer; before, such a token could still read the API.
- **Process editor**: expression fields no longer carry `aria-expanded` on their text area (an accessibility error screen readers and axe report); the suggestions stay announced.
- **Platform page on phones**: the panel with the last connection test no longer squeezes its text to one letter a line next to the periodic test.

## [0.5.0] - 2026-11-04

Steward 0.5.0 makes changes audit-proof and reads more platforms. **Firewall changes** (opt-in, no CMDB): network segments as a system kind, systems in segments with their addresses, the document types _Firewall change_ (`FWC`, four-eyes, evidence, verified by a second person) and _Approved firewall rules_ (`FWR`, a living document per segment or system), table fields for document types, and an optional _Verify_ step on the change workflow. The **assurance policy** (_Settings → Assurance policy_) sets per control point which actions need a second person and which a fresh confirmation, optionally with MFA; baselines cannot be lowered, loosening waits for a second administrator, every confirmed event carries its proof in the audit chain, and the assurance report (PDF/A, JSON, in evidence packs) shows it for a period. Two accounts of one single sign-on identity count as one person. **Microsoft Graph / Entra ID** (read-only, client secret or certificate): access check source, monitor check, credentials import and the bundle _Entra ID access governance_. **IBM Security Verify Privilege Vault 12.0**: permissions and roles for access reviews, secret hygiene, privileged-use evidence and a credentials register link – Steward never reads a secret value. **Export for Postman**: processes and platforms as a collection and an environment, without secrets. Three database migrations, all additive: `catalogue-012-network-segments`, `assurance-001-policy`, `credentials-004-vault-link`. **Check before updating:** nothing changes with the default assurance policy; change requests gain an optional _Verify_ step (closing from _Implemented_ still works); existing installations get the document types `FWC` and `FWR` (an own `FWC` key is kept); the sign-in template variable `baseUrl` no longer ends with a slash; the field names of the vault integration are taken from Delinea's public SDKs – check them against your installation with the checklist in docs/IBM-PAM.md.

### Added

- **Audit-proof firewall changes for network segments and systems** (opt-in, no CMDB, [docs/FIREWALL-CHANGES.md](docs/FIREWALL-CHANGES.md)). Only what needs it is documented – a shopfloor IoT VLAN, a server whose firewall a provider manages; systems in a cloud need nothing.
  - **Network segments**: the system kind _Network segment_ with optional attributes – VLAN ID (1–4094), subnets in CIDR notation (IPv4 and IPv6, format-checked only), zone or security level (e.g. an IEC 62443 zone), site and who manages its firewall (own team or a provider). Everything systems have works for segments (owners, owning teams, environments, CMDB link, documents, _runs on_).
  - **Systems in segments**: any system can be in segments, with an optional address (IP address or host name, format-checked) and a note; the segment lists the systems in it. Who may change the system decides; segments and systems a reader may not see are left out.
  - **Systems are a link kind**: documents, firewall changes and ticket references can name a server or segment directly; a reader who may not see the system sees the link as _not visible_.
  - **Firewall & network** panel on the system page: segments and addresses, the approved firewall rules with their edition and next review, open and closed firewall changes, and the ticket references (e.g. the provider's tickets); records that link to the system under _Linked from_.
  - **Firewall change (`FWC`)**, a built-in document type on the change workflow, also in existing installations: affected segments and systems (links), reason, risk, who implements it (internal or a provider), the provider's ticket, the maintenance window (planned start and end), rollback plan and the rule lines (add/remove, source, destination, protocol/port, allow/deny, enforced at perimeter, host or cloud security group, purpose, expiry). Approved under four-eyes, implemented, **evidence** added (or a run linked), **verified by someone other than the implementer**, then closed. Before closing, each rule line shows what it does to the approved rules.
  - **Approved firewall rules (`FWR`)**, a built-in living document per segment or system: closing a firewall change applies its rule lines and submits the next edition, which an approver confirms – so the document always shows the approved state; a yearly review recertifies the rules.
  - **Process template _Firewall change via provider_** (`examples/processes/87-firewall-change-via-provider.yaml`): request, four-eyes approval, submit to the provider, the provider's confirmation as evidence, an HTTP connectivity check, verification by a second person, close.
  - **Control mappings**: new installations map `FWC` to ISO/IEC 27001 A.8.20, A.8.22 and A.8.32 and `FWR` to A.8.20–A.8.22; the documentation has an importable IEC 62443-3-3 catalogue for SR 5.1 and SR 5.2.
- **Table fields** for document types: rows with fixed columns (text, choice, date; required or not), checked per cell, limited to 12 columns, 200 rows and 500 characters per cell. Shown below the text, edited row by row, compared row by row under _Versions_ and printed as a table in the PDF. The value is JSON in the field, so the content hash and the API stay as they are ([docs/RECORDS.md](docs/RECORDS.md#table-fields)).
- **Verify a change**: the change workflow has an optional step _Verify_ (Implemented → Verified) for someone other than the person who marked the change implemented; _Close_ works from _Implemented_ as before and from _Verified_. Firewall changes require it.
- **Evidence after the approval**: while a change is approved or implemented, editors add evidence files (e.g. a provider's confirmation). They are not content – the approved content and its hash stay unchanged –, each is audited with its SHA-256 and cannot be removed; the PDF lists them.
- **Duplicate systems**: _Duplicate_ on a system or segment copies its attributes, owners and the stack entered by hand; a copied system is in the same segments without the original's addresses.
- API: `POST/PUT/DELETE /api/systems/:id/segments…`, `POST /api/records/:id/evidence`, `GET /api/records/:id/firewall`, `POST /api/systems/:id/duplicate`; `/api/v1/systems` carries `attributes` and `segments`; link kind `system`; attachment kind `evidence`. Migration `catalogue-012-network-segments` (additive: column `systems.attributes`, table `system_segments`).
- **Export for Postman** (#204): a process becomes a Postman collection (v2.1) with one folder – its requests in step order – and an environment for its connections; a platform becomes an environment and a collection of the operations of its API descriptions. **No secret is exported**: every credential, secret input and secret-looking value is an empty environment variable of type `secret`. Sign-ins map to Postman's basic, bearer, API key and AWS Signature auth; OAuth 2.0 client credentials and login requests become a collection pre-request script that fetches the token and keeps it until it expires; key-pair JWT asks for a pasted token. Values a later step reads are set by the test script of the request that produces them; checks become `pm.test(...)` – plain JavaScript for a documented JSONata subset, JSONata itself via `pm.require('npm:jsonata@2.2.2')` otherwise (Postman app and CLI, not Newman). Steps without a request (approvals, manual steps, browser steps, datasets, sub-processes, loops, waits) are listed in the folder description. In the process editor's actions menu and on the platform page; a ZIP with both files, or one of them as JSON (`?file=`). API: `GET /api/processes/:id/export/postman`, `GET /api/platforms/:id/export/postman`; audited as `process.exported_postman` and `platform.exported_postman` ([docs/POSTMAN.md](docs/POSTMAN.md)).
- **Microsoft Graph / Entra ID platform**, read-only: the connector _Microsoft Graph (Entra ID, read-only)_ signs in with OAuth 2.0 client credentials – a client secret or, recommended, a certificate – against the tenant's token endpoint (variables `tenantId` and `loginUrl`; national clouds by base URL and login URL) and brings the Graph read endpoints as its API description for process steps and the MCP gateway. Graph's pages (`@odata.nextLink`) are followed on Graph's own host only, throttling (429/503 with `Retry-After`) is waited out a bounded number of times. The **connection test** names in plain words what is missing: admin consent, each application permission, a licence (Entra ID P1/P2), and explains Entra ID's sign-in errors (`AADSTS…`). Step-by-step app registration and the permissions table in [docs/ENTRA.md](docs/ENTRA.md); demo platform _Microsoft Graph (demo)_ on a simulated tenant.
- **Access check source _Entra ID_**: users and guests by user principal name (e-mail addresses as other names, so **person reviews** span Entra ID and the other platforms), group memberships (nested ones marked) and ownerships, directory roles (active, through role-assignable groups, on administrative units and – with Entra ID P2 – eligible through PIM), app role assignments and disabled accounts; the scope reads one part (`groups`, `roles`, `apps`, `guests`). Last sign-in and MFA registration are reviewer hints. Parts the licence or the permissions do not allow are left out and named (_not available (licence or permission)_), never failing the check ([docs/COMPLIANCE.md](docs/COMPLIANCE.md#access-reconciliation)).
- **Entra ID templates and the bundle _Entra ID access governance_**: guest user review, privileged directory role review (four-eyes), stale accounts, group owner and membership review, expiring app secrets and certificates, with the dashboard _Entra ID governance_ and the example monitor _Entra ID app credentials_. The reviews attest, ask a second person, list the removals for the Entra admin center as a manual step with maker–checker and document them as access changes in the rights the access source reads. The setup wizard and _Get started_ list them for a Graph platform.
- **Monitor check _Entra ID_**: app registrations whose secrets or certificates end within N days or have ended (a rotated one next to its replacement does not count), or the Microsoft 365 service health ([docs/MONITORS.md](docs/MONITORS.md#check-types)).
- **Credentials → Import from Entra ID**: the client secrets and certificates of a tenant's app registrations become register entries with their end date as the expiry, so the register's reminders cover them; a later import keeps their expiry in step with Entra ID (history event _Expiry updated from Entra ID_). Preview first; names, ids and dates only. API: `POST /api/credentials/import/entra` ([docs/CREDENTIALS.md](docs/CREDENTIALS.md#app-credentials-from-entra-id)).
- **Certificate sign-in for OAuth2 client credentials**: a client assertion (RFC 7523 `private_key_jwt`) signed with the platform's private key and naming the certificate by its `x5t#S256`/`x5t` thumbprints, instead of the client secret – _Send client credentials as → Client assertion_, or no secret but a private key. The token scope may use `{{ baseUrl }}` and variables ([docs/PLATFORM-SIGN-IN.md](docs/PLATFORM-SIGN-IN.md#client-assertion-certificate)).
- **Assurance policy** (_Settings → Assurance policy_, [docs/ASSURANCE.md](docs/ASSURANCE.md), #210): one place that shows and sets which actions need a second person (four-eyes) and which a fresh confirmation (step-up). Every such action is a **control point** in one catalogue, grouped by area; per point four-eyes (off / per item / required) and step-up (on or off, a maximum age, **require MFA**). A **baseline** cannot be lowered – the master passphrase, audit anchoring, API tokens, granting access, single sign-on and sign-in settings and the policy itself always need a step-up – and the page shows it locked. Overrides stay where they are (a process step, a platform's MCP mode, a person review, the four-eyes dismissal setting); the page lists every one with the rule that applies. With the default policy everything works as in 0.4.0.
- **New control points with a step-up an administrator turns on** (off by default): approving or rejecting a record (an electronic-signature-like confirmation), documenting or dismissing access check findings, submitting and approving person reviews, verifying a manual step, and closing a firewall change (`firewallChange.close`, records of the type FWC). The policy can also require four-eyes for every run approval, person review, finding dismissal and MCP write (a platform's _confirm_ then needs a second person).
- **Changing the policy**: every change needs a step-up and is audited as `assurance.policy_changed` with before and after. Tightening applies at once; **loosening waits for a second administrator** (approve or reject on the page, shown on _System status_ as a pending policy change, expires after 7 days). The stored policy is sealed; the policy in force at any time comes from the audit chain (`GET /api/assurance/policy/as-of`, `…/history`).
- **Multi-factor per control point**: where MFA is required a password step-up does not count (`ASSURANCE_MFA_REQUIRED`), and a single sign-on step-up needs `amr` or `acr` showing MFA (the policy lists which values count; Steward asks the provider for it).
- **Audit proof per event**: the audit entries of each confirmed or four-eyes event carry the control point, the policy version and rule, requester and approver, the method (password, single sign-on with the provider's `auth_time`, `amr` and `acr`, emergency) and a session reference – inside the HMAC chain. Step-up entries name the session reference too.
- **Assurance report** (PDF/A and JSON, `GET /api/assurance/report`) for a period: the policy in force and its changes, per control point the events and how they were confirmed, and the exceptions (emergency sign-ins, missing MFA, loosening with its second administrator). Download it from the policy page, or include it in an evidence pack (_Include the assurance report_; listed in the signed manifest). Example control mappings: ISO/IEC 27001 A.5.3, A.8.5, A.8.32.
- Migration `assurance-001-policy` (additive): table `assurance_policy_changes`, column `sessions.step_up_detail`.
- **IBM Security Verify Privilege Vault** (12.0, Delinea Secret Server under the IBM name; #205) as a source of evidence – who may use which privileged account, whether rotation works, who used a secret. Steward never reads a secret value ([docs/IBM-PAM.md](docs/IBM-PAM.md)).

- **Verifying the audit chain is incremental**: _Verify chain_, `GET /api/audit/verify`, `GET /api/v1/audit/verify` and report verification check the entries after the newest signed checkpoint (each one is signed only after the entries up to it verified) instead of every entry from #1, so they no longer slow down as the log grows; evidence packs continue the digest from the newest checkpoint as well. `?full=true` (and a pasted checkpoint) checks every entry; after a failed full verification every verification is a full one until one passes again. Republishing a 20,000-row partition next to another one took about 4× less time in the test (median ≈ 38 ms instead of ≈ 170 ms) and no longer writes the 6.6 MB copy. - **Clean stop on SIGTERM/SIGINT.** Steward no longer exits at once: it stops being ready, starts no new runs (`503 SHUTTING_DOWN`) and no scheduled fires, stops report schedules, access checks, backups, background jobs and monitors, gives running steps up to `SM_SHUTDOWN_GRACE_SECONDS` (default 25) to finish, marks what still runs as interrupted, then closes and flushes logs and error reports. Runs waiting for a person are not waited for; they continue after the restart. The compose files set `stop_grace_period: 30s` (Docker's default is 10 s); see _Stopping and restarting_ in docs/INSTALL.md.
- **PostgreSQL: a second instance waits instead of exiting**, and a crashed one no longer blocks the start. The single-instance check is a lease row (`sm_instance_lease`, renewed every 10 s, valid for 45 s) instead of only the advisory lock: a stopped instance hands over at once, a crashed one's lease expires on its own, and the waiting instance answers `/api/health` with 200 and `/api/ready` with 503 until it takes over – no crash loop in Kubernetes and no `pg_terminate_backend` by hand. The advisory lock is still held, so 0.3 and 0.4 never run side by side.
- **Start-up and shutdown order in one place** (`server/src/bootstrap.ts`): recovery of runs, scheduler, monitors and the other services that need the vault start on unlock in a fixed order and stop in reverse; the former start-up file with the warning filter is now `server/src/warnings.ts`.

### Security

- **Availability objectives only name Gatus platforms their author may see** (#86): an unknown or hidden platform is "not found" (no probing of platform ids), and readers who may not see the platform get an objective's status and values but neither the platform nor the endpoint. Documents a reader may not read do not count on the scorecard, also not in the stored daily history (shown as hidden). The scorecard cannot be cleaned by removing history: objectives are archived, never deleted (samples and breaches stay; an archived objective counts with its last status until its longest window has passed), and a duty archived during its current period counts until that period ends. An objective without data for more than 24 hours needs attention (a source turned off or an always-up endpoint chosen to hide a problem shows), breach messages are limited to one per objective a day, and the migration dry run refuses scorecard rows out of range.
- **Exceptions of service duties need a second person** (#85): skipping a period of a duty is a four-eyes decision – the requester (also under a former name of an imported account) can never approve it; administrators, designers and the duty's and the service's owners as they were when it was asked for can (an owner added afterwards cannot, so the requester cannot pick the second person), and they are notified (`duty.exception`). Exceptions reach at most three periods ahead, and the duty shows how many are planned. Before a duty is archived or its process, interval, grace period or level change, its open periods are closed under the old rules, so nobody can erase or re-judge them: a current period without a run that counts is recorded as _ended without a run_ (not met, like missed; stored under its key with a suffix, `2026-10~1`, and for mandatory and recommended duties the owners get the new message `duty.ended`, not the person who made the change), and the new rules start at the moment of the change – no run from before it counts, and no past period is judged again. A change that only makes a duty stricter (a higher level, a shorter grace period) applies to the current period, which stays open. It is not a step-up: it changes no rights or secrets, and both people, the reason and the decision are in the audit log. Duties only name processes their author may view, and people who may not view the process see the status but neither its name nor its runs.
- **Evidence files of manual steps** (#83) are handled like record attachments: allow-listed types whose content must match, at most 20 files of 20 MB per step, written once and read-only with their SHA-256 (a changed file is refused), always downloaded as attachments with a sandbox CSP. Only the person working on the step adds or removes them, and only while the step is being worked on (checked again when an upload finishes); an entry's files are fixed when it is completed. Whoever may see the run reads them. A migration package checks their paths and content again. Verification rights are checked on the server and never let the person who completed a step, or anyone who added evidence to it, verify it, also not under a former name of a moved instance.
- **Mapping a platform to an application needs the manage right on the platform** (#84 review): the mapping decides which application – and whose CIA rating – a platform's evidence pack names, so an application owner who only uses a platform can no longer claim it (or remove it).
- **Protection needs show what they leave out, and say why they moved** (#84 review): a service lists the applications it does not count (archived, not rated, needing re-rating), and every change of an application, of the members or of the scale that moves a service's effective protection need writes `service.protection_need_changed` on that service. A document scoped to an application is also recorded on the application.
- **CIA scale changes that re-order levels, or swap their labels, need a confirmation and flag the ratings** (#84 review); stored scales are validated like a save (an invalid one falls back to the BSI default, every protection need and rating says it is not reliable – UI, public API, evidence packs – and ratings and overrides are refused until an administrator saves a scale; a migration package with one is refused in the dry run).
- **Changing the CIA scale asks for a step-up** (#84): `PUT /api/catalogue/cia-scale` (administrators) maps or flags the ratings of every application at once, so it needs a fresh confirmation like other bulk changes. Ratings, overrides and document scopes are everyday catalogue changes by the people responsible: audited, without a step-up.
- **Sensitive actions ask for a fresh confirmation** (#14): a stolen or unattended session can no longer create API tokens, grant roles, add team members, give anyone a right in an access list (a new or raised entry, the role defaults of an emptied list, a new owner), reset passwords, export the audit log, the credential register or evidence packs, or change single sign-on, sign-in, outbound, notification delivery (SMTP server, webhook URLs, e-mail domains) or audit anchoring settings without the password or a fresh sign-in at the identity provider. The stored SMTP password is never sent to another server: changing the server, port or user, or turning TLS off, needs it again (`SMTP_PASSWORD_AGAIN`). API tokens can no longer use `GET /api/audit/export` and `GET /api/credentials/export.csv`. Single sign-on providers that send no `auth_time` cannot confirm (Entra ID: add the optional claim `auth_time`), see [docs/SSO.md](docs/SSO.md#step-up-re-authentication).
- **Single sign-on claims, hardened after review** (#77): _lower case without @domain_ strips only the domains the provider lists (required) and refuses user names of any other domain, so `boss@evil.example` cannot claim `boss`; a stable identifier must include `sub` or `oid` or custom claims the administrator confirms as unique per person (the confirmed claims are stored and audited, and the confirmation holds only for exactly those claims) – claims many people share (`tid`, `groups`, `roles`, `hd` …, also nested or in another case) are refused (`SSO_STABLE_ID_NOT_UNIQUE`); numbers and strings never give the same link; identifier values are taken exactly as sent (no trimming, joining or cutting; lists, objects and oversized values are refused); the recorded issuer + `sub` changes only when an identity is linked, never at a plain sign-in; user names are NFKC-normalised and limited to letters, digits and `. _ @ + -` when they link an account by name or create one (identities linked already keep signing in); a name that keeps a domain after stripping one is refused; group overage is checked for the configured claim only; `email_verified` comes from the same source as the e-mail address; long (hashed) links survive a kept issuer change; linking a local account ends its sessions; a refused sign-in shows the person only a reference (`SSO_SIGN_IN_REFUSED`) – the reason is in the audit entry; the sign-in page no longer reads accounts.
- **Linking existing accounts at the first single sign-on is a setting per provider** (#77): _only accounts an administrator bound to this provider_ (the default for new providers), _any local account with the same user name_ (what earlier versions did – providers saved before keep it, and the editor warns) or _never_. `email_verified` is now required whenever the e-mail claim names or identifies an account (also with `usernameClaim: 'email'`), unless the provider is marked as verifying every address. Links name the issuer: when a provider's issuer changes, links from before are tied to the former issuer (a person at the new issuer with the same `sub` cannot take the account over) unless the administrator keeps them. An account linked by the configured stable identifier claims is never re-linked to another identity. Group overage indicators (Entra `_claim_names`/`_claim_sources`, `hasgroups`) never grant roles and are logged and audited (`sso.groups_overage`). The editor warns about claims people or other tenants can influence (`email`, `upn`, `preferred_username` with multi-tenant issuers, `name`), a multi-tenant issuer without a required `tid`, Google without `hd`, and stripped domains; every change of the claim settings is audited with the former values. Fields the provider keeps in sync can no longer be changed by an administrator either. Claim values are bounded and control characters removed; the test sign-in never returns tokens or the client secret and is visible only to the administrator who started it.

See [docs/SECURITY-HARDENING.md](docs/SECURITY-HARDENING.md#request-body-limits).
- Adding a documentation link to a platform with a URL that can't be parsed answered `500` instead of `400`.
- **Request bodies are limited to 1 MB by default** (#17, was 25 MB for every route): only the routes that carry a file's content in a JSON body accept more, each sized from its own content limit – the record, control catalogue, monitor, bundle and connector type imports, monitor template instances from CSV, process and dashboard definitions (create, save, validate, convert; 2 MB of text), API specifications (now also at most 20 MB when pasted, as when fetched), the report logo and report verification as base64. They are named in one table (`server/src/bodyLimits.ts`); the route matrix test fails when any other route accepts more than 1 MB. Multipart uploads keep their per-file limits. A body above the limit is answered `413` with the error code `BODY_TOO_LARGE` (`BODY_TOO_LARGE_KIB`) and the limit, translated in the web app. Process inputs, also a CSV table loaded from a file, now fit into 1 MB. See [docs/SECURITY-HARDENING.md](docs/SECURITY-HARDENING.md#request-body-limits).
- Migration packages are refused when their signature, content, file list or audit history does not match; file paths in a package cannot leave the stored-file folders or overwrite files, and uploads are size-limited (`SM_MIGRATION_MAX_MB`) and content-checked. A former user name of an imported account cannot become a new account (also not by single sign-on auto-provisioning), so it cannot inherit that account's grants.
- **The sign-in mode applies to open sessions:** password sessions that the current mode no longer allows (all of them with _Single sign-on only_, those of non-administrators with _administrators also with a password_) end at their next request, and switching the mode signs them out right away. Emergency sessions and the session of the administrator making the change stay. API tokens keep working.
- `steward admin reset-password` refuses while password sign-in is turned off and points to `emergency-access`.
- **Stored files and logos are served with the type of their content**, never with the type a database row (or an imported package) names: run artifacts are shown inline only when they are PNG, JPEG, GIF or WebP images, anything else is a download (`application/octet-stream`, `Content-Security-Policy: sandbox`, `nosniff`); a record attachment of a type uploads never produce is a plain download; the header logo and the report logo take their type from their bytes. So no row can make Steward serve a page or a script on its own origin.
- **Single sign-on claims and sessions:** an account without a password belongs to one sign-in provider (chosen when it is created, _Users → Signs in with_) and only that provider can claim it at the first sign-in; a local administrator account is never taken over by its name – an administrator binds it to a provider first; a user name taken from the e-mail claim needs `email_verified`. The sign-in mode applies by how a session was opened (sessions from before this version count as password sessions), so a password session also ends when its account was linked to single sign-on later. Audit entries of an emergency session are flagged also when a service names the person as the actor (check runs, reports). `SM_PASSWORD_LOGIN=none` on a new installation takes effect once an administrator has signed in with single sign-on, so the setup cannot lock itself out.
- **Migration packages, hardened before the first release:** runs still running or waiting on the source arrive cancelled and are never resumed; a source name that is an account or team here can only become that account or team (never an alias of another one), and former names count as the same person in four-eyes rules, access-change subjects and document authorship; a guess by e-mail address or by the name before "@" needs a confirmation; the manifest signature covers the purpose line `steward-migration-manifest-v1`; the importer enters the source key's fingerprint as read on the source (all 32 hex digits) instead of confirming the value the target shows, and every answer that rests on imported history says so (_verified against the imported audit history of <fingerprint>_; `protocol.importedHistory` in `/api/v1`); the history is checked and taken over line by line (entries at most 4 MB), what a package unpacks to is capped (`SM_MIGRATION_MAX_UNPACKED_MB`, default 20480) and nothing is unpacked without free disk space.

### Security

- **Request body limits against memory exhaustion in validation** ([GHSA-mrhx-c7xc-m3w5](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5), zod): a signed-in user could crash the server with one large request – a list of 12 million items in a 23 MB body made validation allocate 3 GB. Every JSON body is now checked before validation: at most 10,000 items in one list, 10,000 fields in one object, 200,000 values and 100 levels (imports of bundles, connector types and monitors: 50,000 and 1,000,000); above that `413` with `BODY_TOO_COMPLEX`. Requests without a sign-in must give a `Content-Length` (a chunked body skipped the 64 KB limit). See [docs/SECURITY-HARDENING.md](docs/SECURITY-HARDENING.md#request-body-limits).
- **"Superseded by" named records the reader may not read.** The record page, `GET /api/v1/records/{id}` and the record PDF showed the id, number and title of the superseding record (decisions; replaced living documents) even when the reader may not read it, e.g. an access change entry. It now shows as not visible, like links to hidden items (`supersededBy.visible: false` without id, number or title). A decision can only be superseded by a decision record, and a document only replaced by a living document.
- **No owner hand-over while an approval is pending.** Four-eyes compares the approver with the current owner, so the owner of a submitted change request (or a proposed decision, a documented access change) could hand it over to someone else and approve it. Changing the owner is now refused (`RECORD_OWNER_LOCKED`) until the decision.
- **Approvals name the content they decide on.** The transition API takes an optional `contentHash`; the web app sends the hash it shows in the approval dialog, and Steward refuses the decision (`RECORD_CHANGED`) if the record was reworked and submitted again in the meantime.
- **Request rate limits** for the web app's API, the inbound webhooks and the web UI's files ([@fastify/rate-limit](https://github.com/fastify/fastify-rate-limit)): 600 requests per minute and signed-in user, or per client address without a valid sign-in (`SM_RATE_LIMIT_PER_MINUTE`, `0` = off). Counted after the session check, so made-up session cookies or tokens count against the address, including refused (401) requests. Lower limits of their own for expensive actions: 30 per minute for PDF reports, evidence packs, exports, imports and audit verification, 120 for starting runs, checks and platform tests, 10 for password and passphrase changes; webhooks and the web UI's files get a bucket of 10 times the general limit per address. Above a limit: `429` with `Retry-After`, `RateLimit-*` headers and the error code `RATE_LIMITED` (translated in the web app), and one log line per user or address and minute. Health and readiness probes, `/api/v1` and `/api/mcp` (own limiters) are not counted. Counters are in memory, per server process. See [docs/SECURITY-HARDENING.md](docs/SECURITY-HARDENING.md#request-rate-limits).
- Regular-expression denial of service: an administrator uploading a header logo that starts with `<!--` followed by a few hundred `--><!--` blocked the server for minutes (the SVG detection regex backtracked exponentially), and a Markdown link like `[a](` followed by many spaces or tabs took seconds to minutes to render (records, notes, report text – on the server and in the browser). Both are now linear scans. (CodeQL `js/redos`, `js/polynomial-redos`)
- Files in the data folder (run screenshots, PDF reports, platform documents) and the monitor examples are opened through one helper that only accepts plain names and refuses any path outside its folder. The ids were already looked up in the database first, so this is defence in depth.
- Traces (OpenTelemetry, off by default) carry the user as a keyed hash with a per-installation key instead of a plain SHA-256 of the user name, so whoever holds the traces cannot re-identify users by hashing known names.
- CodeQL no longer scans test code (`server/test`, `e2e`), which is not shipped; everything else, including the demo mock servers, still runs with the `security-extended` queries.

### Fixed

- `GET /api/runs` returns a full page (up to `limit`) even when many runs belong to processes the user may not see; before, a page could end early and look like the end of the list.
- **Node.js 26: crash after a few minutes** (`Check failed: IsCompatibleCode` in `Genesis::InitializeGlobal_regexp_linear_flag`, exit code 133): the expression engine switched V8's experimental regexp engine on with `v8.setFlagsFromString()` while running, which Node documents as undefined behaviour; every worker thread started later (the regular expression guard, the PostgreSQL bridge) then built its context with the flag, and Node 26 aborted there. Steward no longer changes V8 flags at runtime (an ESLint rule and a test keep it that way) and needs no V8 flag at all: regular expressions in process expressions run natively only when they are fixed-length (no quantifier, alternation, back reference or lookaround – bounded work); all others run in the worker thread with its time limit, which now returns a batch of matches per round trip. A catastrophic pattern such as `/(a+)+$/` now fails after 500 ms with "simplify it" instead of being rescued by the linear engine. Node.js 26 is supported and tested in CI next to Node.js 24 (LTS, the primary version); `engines` is `^24.0.0 || ^26.0.0`.

### Security

- Expressions: regular expressions such as `/\u{0,99}X/` (without the `u` flag `\u{…}` is a letter with a quantifier) were classed as fixed-length and ran on the main thread, where a crafted pattern could block the server; they now run in the time-limited worker like every other quantified pattern.

- Regular expressions that relied on the V8 linear-engine fallback (see _Fixed_) work in linear time without it: the JSON Web Token mask of error reports (was quadratic on long `-eyJ-eyJ…` runs) and the Prometheus value parser of the Gatus metrics scraper (quadratic on long digit runs). Error-report scrubbing caps every string at 8 192 characters before its patterns run (known secrets are still removed from the whole string first), so no string takes more than about a second.
- Git sync review fixes: the _Updates from Git_ inbox hides updates of processes and monitors the reviewer cannot see (no name, no current definition; detail, accept and reject answer 404); blobs of SHA-256 repositories are checked against their object ids too; _Require signed commits_ checks every new commit since the last fetched commit through the hosts' compare/commits APIs (not only the branch head), refuses the whole fetch if one is unverified (nothing staged, audited) and can be limited to allowed signers (logins or e-mail addresses); superseded updates are deleted and the content of rejected ones removed after 30 days; one `sync.fetched` audit entry per fetch lists the staged files instead of one entry per file.
- Git sync: repository hosts must pass the outbound policy; the access token is vault-encrypted, never returned and only sent to the source's API base (redirects refused); responses are size-capped, blobs checked against their Git object ids, paths confined to the folder, YAML parsed as plain data, files with secret-looking values refused; optional signed-commit requirement; source configuration needs a signed-in session; the push webhook is HMAC/secret-authenticated and rate-limited; every fetch, staging and decision is audited.
- Evidence packs only contain what the requester may see (the audit log excerpt only for auditors and administrators), are size-limited, written to disk as they are built and deleted after the retention period; requesting, building and downloading them is audited.
- Access governance (review round 3, see [docs/COMPLIANCE.md](docs/COMPLIANCE.md)):
  - Access change entries are written and documented only by people who may use the platform, and read only by administrators, auditors, approvers, their owner and who has a right on the platform – also in record lists, search, links, backlinks, coverage, evidence packs, reports and `/api/v1`. Before, every signed-in user read them, and an operator without rights on a platform could close its reconciliation findings.
  - Nobody documents, dismisses or verifies a change of their own access (subject matched by user name or e-mail address); an entry documented by its subject does not close a finding. A finding is closed by a later entry only when the person who documents it may document the findings of the check.
  - Entries of runs name the person who started the run as performer; that person and the run's approvers cannot verify them, and nobody can change or revise them. Origin, run and finding of an entry are set only by Steward (`400 ACCESS_FIELD_RESERVED`). Entries show who documented them and who last edited them; entries changed in the database are flagged (`tampered`) and do not count.
  - Dataset checks need the right to view the process that publishes the dataset (when set up and on every run); the dataset key of a check with snapshots cannot change. Ignored rights are set by administrators only and audited with the old and new list (as are the recipients). Optional four-eyes dismissals (_Settings → Access reconciliation_).
  - _Verify history_ compares snapshots and findings with the authentic audit entries: deleted snapshots (also the newest), deleted findings and statuses changed in the database are reported; database triggers refuse deleting snapshots and findings.
  - Evidence packs: the offline check reports a pack signed with a key nobody confirmed as _UNTRUSTED_ and exits with 3 – pass `--public-key`, `--fingerprint` or `--trust-pack-key`; it always prints the key fingerprint. Manifest signatures are domain-separated from audit checkpoints (version 2 manifests; older packs still verify). The ZIP reader refuses bytes outside the listed entries, gaps, overlaps and local headers that differ from the central directory. Packs of someone who cannot see everything say so and count the evidence left out per control (_not visible_ instead of _gap_).
  - Mapped control items the reader may not see no longer show their id and cannot be removed by them.
  - The Insights Hub collector applies its limits while it reads the pages (rights per user, users, assignments; 16 MB per page).
  - YAML imports (control catalogues – now at most 256 KB –, processes, dashboards, monitors, API specifications, record front matter, Git sync files) are size-capped before parsing and check duplicate keys in linear time: the YAML library's own check is quadratic (40 000 keys took 20 seconds).
- Holistic review (OWASP ASVS 4.0.3 level 2), see [docs/REVIEW-2026-10.md](docs/REVIEW-2026-10.md):
  - API specifications and operations of a platform (`/api/platforms/:id/specs`, `/operations`, `/api/specs/:id/content`) were readable by every signed-in user; they now need a permission on the platform, like the platform itself.
  - API tokens can no longer manage users, teams, single sign-on providers, sign-in and outbound settings or the master passphrase (`403 SESSION_REQUIRED`): before, a leaked full-access token of an administrator could create a new administrator or reset a password and so outlive its revocation.
  - Sessions end after 30 minutes without a request and 12 hours after sign-in (before: 12 hours idle, 7 days); `SM_SESSION_IDLE_MINUTES` and `SM_SESSION_MAX_HOURS` change it. Over HTTPS the session cookie has the `__Host-` prefix (everyone signs in again once after the update).
  - Single sign-on: sign-ins in progress (started without signing in) are capped at 5000 and the return path at 1 KB – a flood of `/api/auth/oidc/:id/start` requests could exhaust the server's memory.
  - Changing the own password: at most 5 wrong current passwords per 15 minutes, each one audited (`user.password_change_failed`).
  - Webhook mapping preview only for people who may run a process; at most 100 mapped inputs and 5 s per evaluation.
  - Query strings are validated (repeated or malformed parameters gave HTTP 500, `limit=-1` unlimited lists); database errors are no longer returned to the client. Size limits for user, team, platform, schedule, task decision and process text fields.
  - Startup warnings for risky settings (no HTTPS with extra host names, demo mode on a network address, the passphrase in an environment variable, public metrics, long sessions).
  - `server/test/route-matrix.test.ts`: every route is called by every role, without credentials and with read-only and MCP tokens; a new route fails the test until its access rules are classified.
- Credentials register: no field holds a secret; free text, links and comments are checked for private keys, JWTs, well-known token formats, passwords in URLs and random-looking tokens and refused (the value is never echoed); only `http(s)` links are clickable (`javascript:`/`data:` refused); uploaded certificates are parsed and only their metadata is stored, files with a private key (PEM, DER, PKCS#12) are rejected; CSV exports are protected against formula injection.
- Gatus metrics mode: `/metrics` is unauthenticated in Gatus – the docs require it to be network-restricted. Steward fetches it through the platform and the outbound policy, only below the platform's base URL, with an 8 MB limit, a timeout and a bounded parser.
- E-mail to addresses outside Steward (credential owners, report recipients): only to allowed domains – the new setting _Settings → Notifications → Allowed e-mail domains for addresses outside Steward_ (`corp.example`, `*.corp.example`); while it is empty, the domains of the users' own addresses that an administrator, a single sign-on account or at least two users use. Checked when saving and again on every send. At most 10 addresses per credential entry and 20 per report schedule; owners who edit an entry only as its owner cannot change its owner addresses. Subjects carry user-chosen names only quoted after a fixed prefix and shortened to 80 characters.
- Report schedules: cron expressions with seconds are refused, a schedule runs at most once an hour (also schedules saved before), at most 20 schedules per owner.
- Certificate upload: PEM blocks are found in one linear pass, with at most 21 BEGIN lines (a file with many BEGIN lines without END blocked the server for seconds).
- Monitors: viewers of a monitor that includes a sub-monitor they may not view no longer see its id, key, name or check names – in root causes, _likely caused by_, the sub-monitor check, messages, history, the definition and YAML export, the `monitor.<key>` dataset, `/api/v1/monitors…`, the MCP tools and notifications ("a monitor you cannot view"). The sub-monitor check's message no longer names the monitor.
- Credentials register: the name of a linked platform is only shown to users with a right on it, and editors can only link platforms they may see (an unknown and a hidden platform get the same answer).
- Gatus metrics mode: the metrics path refuses encoded dots and slashes (`%2e`, `%2f`, `%5c`) and the resolved URL must stay below the base path; _Scrape now_ at most every 15 s per platform; deleting a platform deletes its Gatus data, and endpoints not seen for the history period are removed.
- MCP (new): its own token scope that no other API accepts (and MCP endpoints accept no other scope); `Origin` validation against DNS rebinding next to the `Host` allow-list; 64 kB request limit, no batches, strict argument schemas, per-token rate limits and time limits; tool output is structured JSON marked as untrusted data. The platform gateway is opt-in per platform, read-only (writes are refused and audited), builds paths only from the API specification or allow-listed prefixes (no absolute URLs, dot segments or encoded separators), validates query parameters, applies the outbound policy, does not follow redirects, caps responses at 512 kB, masks credentials and returns no cookies.
- Records: uploaded attachments are checked against their extension (magic numbers, e-mail headers, UTF-8 text), stored read-only with their SHA-256 (checked on download) and always downloaded as attachments in a sandbox; Markdown is rendered from a syntax tree without HTML (links: http, https and mailto only); YAML frontmatter is parsed with the core schema only (no custom tags, aliases limited) and sizes are limited; links only name targets the reader may see; a signed PDF is only accepted when its first bytes match a generated PDF of the record whose audit entry is authentic.
- Security review fixes (MCP, gateway, API v1):
  - `GET /api/v1/platforms` and `/platforms/{platformId}` only show platforms the token owner has a permission on (as the web UI does); others answer `404`;
  - the MCP stdio bridge no longer sends the token to a local URL while the data folder has no `instance.json`: it waits briefly (`--wait`), then fails; after a lost connection it checks the proof again; `--no-instance-check` (documented as less safe, with a warning) is for setups such as Docker on `localhost`;
  - credentials are masked in more encodings in run journals, logs and gateway responses: form encoding (`URLSearchParams`, e.g. `~` as `%7E`), RFC 3986 strict encoding and lowercase hex – for example a query API key echoed in a `Link` header;
  - the gateway refuses `;` in paths and path parameters (`..;/` is a dot segment for Tomcat, Jetty and Spring);
  - gateway audit entries escape control characters in client-chosen names and log invalid paths as `(invalid)`;
  - gateway rate limits apply per user and platform (not per token), and at most 2 gateway calls per platform run at the same time (`SM_MCP_GATEWAY_CONCURRENCY`), so runs and monitors keep their connection slots.
- Records (security review): the Markdown parser and the PDF engine (records, run and scheduled reports) work in linear time – unclosed brackets or emphasis, long lines of spaces, table cell bombs and very long words no longer block the server or the browser (words get invisible break opportunities, a PDF draws at most 1 000 000 characters); the Markdown import reads titles and comments without backtracking regular expressions; the signed-PDF scan reads each signature in a bounded window and a record keeps at most 100 generated and 30 signed PDFs (300 MB). Four-eyes counts everyone who attached or removed files and the authors of earlier revisions (a new revision no longer launders them). Before a transition the content hash must also match the authentic audit entry that froze the revision (a recomputed `frozen_hash` in the database is detected). The key of a record type with records cannot change any more (it is part of their content hash). Links to items the reader may not see no longer return the target id (API, UI, PDF) and `/api/backlinks` answers 404 for them; links of closed records cannot change. Signed PDFs are only accepted for the current, frozen revision and only with signature values and complete byte ranges; signer names are shown as claimed, not verified. Frozen records keep the field definitions they were approved with.
- Platform credentials are no longer sent to hosts outside the platform when a step calls an absolute URL.
- The vault rejects shortened AES-GCM authentication tags.
- Audit log integrity (review C):
  - verification fails on rows with a sequence number below 1, on rows outside the chain, and on entries removed while the server runs; the database refuses such rows (migration `security-001`);
  - every hour, on each verification and before each export a checkpoint `{seq, hash, digest, count, ts}` is signed with a per-installation Ed25519 key kept in the vault; it is written to the audit log, to `audit-anchor.json` in the data folder and as a log line for the SIEM, and can be e-mailed to auditors (_Audit log → Anchoring_);
  - verification compares the chain with these anchors and with an external checkpoint (pasted in the UI, `SM_AUDIT_ANCHOR`, `SM_AUDIT_ANCHOR_FILE`): removing the newest entries or wiping the log is detected;
  - exports include `prevHash`, details and a signed checkpoint; `npm run audit:verify-export` checks an export offline with the public key;
  - report verification, protocol seals and summary reports only trust audit entries whose HMAC and chain position check out – a forged row no longer makes a forged PDF verify;
  - audited free text is capped, failed sign-ins are summed up per account/address and minute, and entries recorded while the vault is locked are bounded (dropped entries are counted in the log); unauthenticated requests may send at most 64 KB.
- Sessions are bound to a per-session key that the web app keeps in its origin's `localStorage` and sends as `x-sm-session`; a session cookie received by another program on the same host no longer signs anyone in. Download links carry a read-only link key. **Everyone has to sign in again after the update.**
- The master passphrase can be read from a file (`SM_MASTER_PASSPHRASE_FILE`: Docker secrets, systemd credentials); both passphrase variables are removed from the environment at start. Browser steps start Chromium with a minimal environment and with its sandbox (unless running as root); the desktop launcher starts the user's browser without `SM_*` variables or secrets.
- Vault format 2: random data, audit, integrity and signing keys wrapped with a scrypt key (N=2^17); existing vaults are converted on their first unlock (the audit chain stays valid). Administrators can change the master passphrase (_Settings_), optionally rotating the data key; new passphrases need 12 characters; wrong passphrases are audited and throttled.
- Platform connection settings (base URL, authentication, token URL, trusted origins, headers) and sign-in provider settings are sealed with an HMAC; when they are changed directly in the database, no requests are sent until an administrator confirms them.
- Password checks run off the event loop with a concurrency limit and the same cost for unknown user names.
- The desktop launcher only opens its window for a server that proves it knows the secret in the user's data folder (port squatters are refused).
- Data folder `0700`, database, vault and key files `0600` on Linux/macOS (existing installations are fixed at start).
- Audit CSV export escapes cells that spreadsheets would run as formulas.
- `SM_TRUST_PROXY` for reverse proxies (real client addresses for the audit log, lockouts and webhook CIDRs); `Secure` cookie and HSTS with an `https://` `SM_PUBLIC_URL`.
- Failed sign-ins with user names that belong to no account store a pseudonym instead of the typed text; new process input type _secret_ (stored encrypted, `***` everywhere).
- Redaction of JSON-/URL-/Base64-encoded secrets, Basic credentials and OAuth token fields in run data; error reports scrub encoded secrets; traces carry a user pseudonym and scrubbed exception messages; TLS 1.2+ with forward-secret ciphers; `Cache-Control: no-store` on API responses; the desktop executable re-checks its unpacked files at every start; hardened compose files.
- Supply chain: `npm ci --ignore-scripts` plus an enforced install-script allow-list in CI, release builds and the Dockerfile; signed build provenance and SBOM attestations for release archives and the container image.
- New: [docs/SECURITY-HARDENING.md](docs/SECURITY-HARDENING.md) (checklist for a work deployment) and [docs/PRIVACY.md](docs/PRIVACY.md).
- Every process expression now runs under guard rails by default — a time limit (`SM_EXPR_TIMEOUT_MS`, default 5 s), stack-depth and sequence-size limits (`SM_EXPR_MAX_DEPTH`, `SM_EXPR_MAX_SEQUENCE`), a heap watchdog and regular expressions that cannot backtrack catastrophically — and long evaluations yield to the event loop, so a single expression can no longer freeze the server (DoS).
- Resolved secret values (`$secret()` and platform credentials) may only leave Steward towards the platform's own allowed origins: outbound requests are scanned for any bound platform's secret (also base64/URL-encoded) and the step fails if one would reach another origin. Secrets are masked in their encoded forms in logs too.
- Credentials are re-evaluated on each redirect hop: custom-named API-key headers, default headers and any header carrying a secret are dropped when a redirect leaves the allowed origins, and `https → http` downgrades that would carry credentials are refused (redirects are followed manually, max 5 hops).
- New outbound destination policy (SSRF protection) for process-controlled requests — `http` node, pagination, browser navigation and sub-requests, OpenAPI import by URL — configurable under _Settings → Outbound access_ (`platforms` / `allowList` / `open`, `SM_OUTBOUND_POLICY`). Cloud-metadata and link-local addresses and the server's own API port are always blocked, and the resolved IP is pinned for the connection (no DNS rebinding).
- Dashboard datasets are owned by the process that first publishes a key; another process can no longer overwrite it or hijack its dashboard visibility.
- Dry runs can be made read-only for a browser step (`dryRunReadOnly`), and a dry run now warns in the protocol when a browser step performs page interactions that could change data.
- Monitors adopt the same policies: http/tcp/ping checks and webhook/Zabbix outputs are subject to the outbound policy (DNS-pinned; raw `host:port` checks need an explicit allow-list entry such as an IP/CIDR and are not inferred from platform origins); monitor http checks follow redirects manually and drop custom headers cross-origin; check error messages no longer echo the upstream response body; the guarded expression evaluation bounds condition/heartbeat/freshness expressions (CPU, memory via a `$pad` cap, and regex time); and gateway heartbeat batches share a global evaluation-concurrency cap (`SM_MONITOR_EVAL_CONCURRENCY`).
- Semgrep findings triaged (all rule sets of the CI job, see [docs/SECURITY-PIPELINE.md](docs/SECURITY-PIPELINE.md#semgrep-triage)): the dev, PostgreSQL-test and install-script helpers start npm without a shell, also on Windows (`scripts/npm-command.mjs`); monitor-gateway key patterns (glob) and the API path editor match without regular expressions built from configured data; translation lookups ignore inherited properties; the CI gate also blocks HIGH/CRITICAL findings; SARIF uploads get the `actions: read` permission they need.
