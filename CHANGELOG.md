# Changelog

All notable changes to Steward are documented here.

The format follows [Keep a Changelog 1.1](https://keepachangelog.com/en/1.1.0/), and the project uses [Semantic Versioning](https://semver.org/). Commits follow [Conventional Commits](https://www.conventionalcommits.org/), so entries can be drafted from the commit history.

## [Unreleased]

### Added

- **Team-scoped access, part 1** (#131): processes, platforms and the service catalogue (services, applications, systems) can have **owning teams**. Members of an owning team have their instance roles and the **roles they have in that team** on it (a viewer can be a designer in team Orders); everyone else sees the resource only through an access list entry (an exception for sharing across teams), and administrators have every right, auditors may view. A resource without an owning team behaves exactly as before. In the catalogue, members of an owning team see the item and change it when they are designers there, its named owners as before; an application without teams of its own belongs to the teams of its services; others do not find it in lists, details or link pickers. The web app shows the owning teams on every such page, with _Why do I have access?_, and team roles in the team editor. One policy module (`server/src/auth/policy.ts`) decides and explains: `GET /api/access/explain?kind&id[&user]` names where each right comes from ("designer in team Orders", "access list user:dave", "instance role auditor"). Owning teams are set with `PUT /api/owning-teams/{kind}/{id}` (administrators; adding a team is confirmed with a step-up), roles in a team with `memberRoles` on the team; both are audited and move with migration packages through the identity mapping. Migration `teams-001-scopes` (additive: a column and a table, nothing set on existing data).

### Changed

- **Route access is declared on the route and checked before the body is read** (#16): whether a route is public, a webhook, for signed-in sessions only (no API tokens), for certain roles, or open to status viewers is now part of the route's configuration instead of lists in `app.ts`. One check reads it for every request, before the request body is parsed, so a caller who may not use a route gets 401/403 without their upload or JSON being read. 65 administrator-only routes (settings, users, teams, single sign-on, backups, migration, theme, report branding, notification settings) now refuse other roles this way. The sign-in check (`me()`) and `forbid()` exist once, in `server/src/auth/access.ts`, instead of in 17 modules. The route permission test compares the declarations with its table. Status viewers may log out, change their password and confirm their sign-in, as they could before.
- **Development: vitest 5 and a coverage report** (#24, #23, #22): the server tests run on vitest 5. `npm run test:coverage` measures coverage; CI does so on Node 24, lists the totals and the least covered files in the job summary and keeps the HTML report for 14 days (a report, no minimum yet). Browser-test servers start on a free port of their own choosing and report it in their start line.
- **Coverage says "not visible" instead of "gap" for evidence you may not see** (#21): the Controls page and the read API now use the rule of evidence packs. A control with evidence in the period that the reader may not see shows _Not visible (n hidden)_; a covered control says how many more items are hidden. **API:** `GET /api/v1/control-coverage` returns the new `status` value `notVisible` and a `hidden` count; a client that accepts only `covered`, `gap` and `unmapped` has to accept it.
- **PDFs are drawn in a worker thread** (#13): run reports, summary and scheduled reports, PDFs of records and the summary of evidence packs are drawn apart from the thread that answers requests, one at a time, stopped after 60 s (`PDF_TIMEOUT`) or 512 MB (`PDF_TOO_LARGE`); with 20 waiting, the next one is refused (`PDF_BUSY`). The data is collected first; drawing reads no database. `SM_PDF_WORKER=off` draws in the main thread as before; with `auto` (default) Steward falls back to that when the worker cannot start. _System status_ shows which applies. See [Reports](docs/REPORTS.md#how-pdfs-are-created).
- **Audit checkpoint e-mails follow the allowed e-mail domains** (#18): auditors' addresses outside Steward need an allowed domain (_Settings → Notifications → Allowed e-mail domains_), as report recipients and credential owners do; saving a recipient with another domain is refused (`EMAIL_DOMAIN_NOT_ALLOWED`). **Check before updating:** add the domain of an external auditor or archive mailbox to the allowed domains, or its checkpoint e-mails stop.
- **Development: shared helpers and smaller route files** (#18): one CSV writer (`server/src/csv.ts`; the audit, credential and evidence-pack CSV files are unchanged), one e-mail address rule (`isEmailAddress` in `shared`) for profiles, credential owners, service contacts, report recipients, record signers and auditors, and one way out for e-mail (`notifications/email.ts`). The route registration (`routes/index.ts`) and the read API (`api/v1/routes.ts`) are split by area, with the same routes, access rules and OpenAPI document.

## [0.2.10] - 2026-10-31

AI assistants can now ask for changes instead of only reading: a changing platform call or a run requested through MCP becomes a request that a person confirms – per platform by the token owner or, four-eyes, by an approver – and runs once, as its requester. **Service status pages** show colleagues outside the service team how their services are doing – from the monitors, maintenance windows, objectives and known vendor issues, without names or tickets – to a new status viewer role or through a secret link without sign-in. Dashboards get a **Vega-Lite chart widget** for the few views the built-in widgets do not cover, drawn from the widget's dataset only and without `unsafe-eval` in the Content Security Policy. Two database migrations, both additive: `ops-012-mcp-requests` and `catalogue-010-status-pages`.

### Added

- **Vega-Lite chart widget** (#120): a dashboard widget `vega` draws a [Vega-Lite](https://vega.github.io/vega-lite/) spec from its dataset, for the few views the built-in widgets do not cover – with a table view, the theme's colours (schemes `steward` and `steward-status`) and a spec editor that checks as you type. Only the dataset is shown: specs that load data or images (`url`), link (`href`) or carry their own data are refused when saving. Expressions run in vega-interpreter, so the Content Security Policy stays without `unsafe-eval`, and the chart chunk is loaded only on dashboards that use it. Examples on _Edge fleet_ (devices per firmware version) and _Tenant usage_ (used share of each limit) ([README](README.md#dashboards)). New dependencies: `vega`, `vega-lite`, `vega-interpreter` (web).
- **Service status pages** (#26): read-only pages for people outside the service team – per service the state from its linked monitors (counts only, no names), planned and running maintenance, known issues with vendors (the vendor and since when, never the ticket) and optionally the availability objectives, plus a notice. A new role _status_ (status viewer) sees nothing but the status pages, enforced once on the server for every route. A page can get a secret link without sign-in, stored as a hash, kept in the URL fragment so no log sees it, revocable and audited ([docs/STATUS-PAGES.md](docs/STATUS-PAGES.md)). Migration `catalogue-010-status-pages` (additive).
- **Approved writes through MCP** (#11): an AI assistant can ask for a changing platform call (POST, PUT, PATCH, DELETE) through the MCP gateway, or to start a run – it never happens when it asks. Each becomes a request under _AI requests_ that the token owner confirms or, per platform, a second person (an approver or administrator who may use the platform) approves; it then runs once, as the token owner, with the rights and settings of that moment, and expires after 24 hours otherwise. Changing calls are off per platform (turning them on needs a fresh confirmation of the sign-in), run requests are off for the instance. Decisions only with a signed-in session, new notification event _Request from an AI assistant_, every step audited, `get_operation_request` and `request_run` tools ([docs/MCP.md](docs/MCP.md#approved-writes)). Migration `ops-012-mcp-requests` (additive).

### Fixed

- Two example dashboard titles lost the text after their comma (_Users, assets and agents over time (%)_ on _Tenant usage_, _Critical, high and failing policies_ on _Vulnerabilities_); a test now catches unknown widget keys in the examples.

## [0.2.9] - 2026-10-31

Steward reads the vulnerabilities of the software it runs and reviews one person's access across platforms at a time. **Dependency-Track** projects can be named on any application component: Steward reads their open findings and policy violations, records new critical findings in the application's history, adds the part _Vulnerabilities_ to the service scorecard and a monitor check type. **Person access reviews** collect everything one person may do across several access checks – read live, frozen, decided right by right, approved by a second person and sealed – and check later that the rights to remove are gone; approved reviews count as evidence of their access checks. AWS IAM becomes an access check source. Three database migrations, all additive: `catalogue-009-dependency-track`, `scorecard-004-vulnerabilities` and `compliance-003-person-reviews`.

### Added

- **Dependency-Track** (#119): a platform type _Dependency-Track_ (API key). Any application component names its project – `name@version`, `name@latest` or the UUID; every 6 hours or on _Read now_ Steward reads the open findings by severity (suppressed ones and those analysed as not affected or false positive do not count), the policy violations, the risk score and the most important findings with EPSS and the fixed version. A new critical finding or failing policy goes into the application's history. The service scorecard gets the part _Vulnerabilities_, and monitors the check type `dependency-track` (critical and high findings, failing policies). A demo instance ([docs/DEPENDENCY-TRACK.md](docs/DEPENDENCY-TRACK.md)). Migrations `catalogue-009-dependency-track` and `scorecard-004-vulnerabilities` (additive).
- **Person access reviews** (#118): _Compliance → Person reviews_ collects everything one person may do across several access checks – read live (or from the latest snapshot), matched by their user names and e-mail addresses, and frozen. The reviewer decides keep or remove per right (a removal needs a reason, nobody reviews their own access), a second person approves or sends it back, and the review is sealed with a SHA-256 over all decisions that can be verified. _Check removals_ reads the platforms again and closes the review when every right to remove is gone. Approved reviews are evidence of their access checks on controls and in evidence packs. New access check source _AWS IAM_ (users with groups, managed and inline policies, technical users marked) ([docs/COMPLIANCE.md](docs/COMPLIANCE.md#person-access-reviews)). Migration `compliance-003-person-reviews` (additive).

## [0.2.8] - 2026-10-30

Steward signs in to more platforms and looks after itself. Platforms can sign in with a **key-pair JWT** (Snowflake, Google service accounts) or **AWS request signing** (SigV4, written out and checked against AWS's own examples – no AWS SDK), also as an assumed role. Steward makes **encrypted backups to S3** on a schedule: a consistent copy of the database and the data folder, encrypted with a backup passphrase that is never stored, kept by a grandfather–father–son rule and tested by a weekly restore test that decrypts and checks every file and the audit chain. **AWS accounts** show the resources, costs and IAM keys of each application by its tag; **Snowflake** accounts show databases, failing tasks and warehouse credits, feed access reviews through the role hierarchy and a monitor check. Two database migrations, both additive: `ops-011-backup-runs` and `catalogue-008-cloud-readouts`.

### Added

- **Platform sign-in: key-pair JWT and AWS request signing** (#114). _Key-pair JWT_ signs a short-lived JWT (RS/PS/ES algorithms, at most an hour) with the platform's private key, with templated claims and the public key fingerprint – sent as the token (Snowflake) or exchanged for an access token (RFC 7523). _AWS request signing_ signs every request with Signature Version 4 (checked against AWS's documented examples, no AWS SDK), with an access key or an assumed role (STS AssumeRole, external ID, renewed before it ends), for AWS APIs, S3 and S3-compatible storage. Both work with the connection test, _Get a new token_ and the MCP gateway ([docs/PLATFORM-SIGN-IN.md](docs/PLATFORM-SIGN-IN.md)).
- **Backups to S3** (#117): on a schedule (default 02:15 daily) Steward copies its database – a SQLite snapshot while it runs, or `pg_dump` of the PostgreSQL schema – and its data folder into a ZIP with a SHA-256 manifest, encrypts it with AES-256-GCM in authenticated chunks under a key from a backup passphrase (scrypt; the passphrase is never stored) and uploads it to an S3 bucket or S3-compatible storage through a platform with AWS request signing (multipart for large files). A grandfather–father–son rule keeps 7 daily, 4 weekly and 12 monthly backups; S3 Object Lock is respected. A weekly restore test downloads the newest backup, compares its checksum, decrypts it and checks every file, the SQLite integrity and the audit chain of the snapshot (PostgreSQL: `pg_restore --list`). Failures notify the administrators (new event _Backup failed_); runs, settings and passphrase changes are audited. _Settings → Backups_, the offline tool `npm run backup -- decrypt|verify|info` (desktop: `steward backup …`), `postgresql-client` in the container image and a mock S3 in the demo ([docs/BACKUPS.md](docs/BACKUPS.md)). Migration `ops-011-backup-runs` (additive).
- **AWS accounts** (#116): a platform type _Amazon Web Services (AWS account)_ – one account, signed with SigV4 per service, an access key or an assumed role, the connection test asks STS who it is. Application components of type _Cloud account_ name it with the value of the application tag (`application=shop`): Steward lists the resources with the tag in the configured regions (Resource Groups Tagging API), the costs per month for the tag (Cost Explorer, read at most once a day) and the IAM users with the tag and the age and last use of their access keys, which can be added to the credentials register; every 6 hours or on _Read now_, one shared read per account, resources that came or went in the application's history. A demo account with a mock that checks every signature ([docs/AWS.md](docs/AWS.md)). Migration `catalogue-008-cloud-readouts` (additive).
- **Snowflake** (#115): a platform type _Snowflake (SQL API)_ with key-pair JWT sign-in, statements with bind parameters only, read from the `ACCOUNT_USAGE` views. Application components of type _Snowflake database_ show the tables with size and last change, the tasks that failed in the last day and the credits of the warehouses used (every 6 hours or on _Read now_; a newly failing task in the application's history). Access reviews get the source _Snowflake_: the roles of every user, or who reaches a database, schema or table through the role hierarchy, technical users marked. Monitor check type `snowflake`: freshness of a table (current, from `INFORMATION_SCHEMA`), failing tasks, warehouse credits. A demo account whose mock verifies every JWT ([docs/SNOWFLAKE.md](docs/SNOWFLAKE.md)).

## [0.2.7] - 2026-10-30

Steward reads the platforms applications are built and run on. **GitHub, GitLab and Forgejo/Gitea** become connectors: repository components show the pipeline of the default branch, the latest release, open security alerts, packages, deploy keys and tokens (offered for the credentials register) and the tech stack read from Dockerfile, package.json, go.mod and similar files; a monitor check follows the pipeline, and access reviews read organisation and repository members. **Kafka** topics of applications – Confluent Cloud or any Kafka cluster, read with a read-only service account – show their settings, consumer lag and schema version; monitors check new messages, lag, stuck consumer groups and the schema; a guarded peek reads a few messages for troubleshooting. **MQTT** brokers get a monitor check for messages within a window, silent devices and connected clients, keeping only times and counts per topic. Two database migrations, both additive: `catalogue-007-component-readouts` and `ops-010-mqtt-topics`.

### Added

- **Git platforms** (#107): platform types _GitHub_ (also Enterprise Server), _GitLab_ and _Forgejo / Gitea_ with a read-only token, a connection test and a small API description each. Application components of type _Repository_ name their Git platform and repository path; Steward reads the default branch and its pipeline (workflow runs, GitLab pipelines, commit status), the latest release, open Dependabot alerts, packages and container images, deploy keys and GitLab deploy and access tokens – each can be added to the credentials register after review – and the tech stack from Dockerfile, package.json, go.mod, .nvmrc, .tool-versions, global.json, composer.json and pom.xml (source _read from the repository files_), every 6 hours or on _Read now_. Monitor check type `git` (pipeline of a branch, optional alert limits), access reviews with the source _Git_ (organisation, group or repository members with their role, outside collaborators marked), the example _GitHub – repository health_ with the dashboard _Repositories_, and demo hosts ([docs/GIT-PLATFORMS.md](docs/GIT-PLATFORMS.md)). Migration `catalogue-007-component-readouts` (additive).

- **Kafka** (#112): a platform type _Kafka cluster_ for Confluent Cloud and Platform, Apache Kafka, Redpanda, MSK and Event Hubs – bootstrap servers with SASL (PLAIN, SCRAM, OAUTHBEARER) over TLS through a pure-JavaScript client, the Schema Registry as its base URL. Application components of type _Kafka topic_ name their cluster; Steward reads settings, partitions, the newest message's time, consumer groups with their lag and the schema version every 6 hours or on _Read now_ (a new schema version is recorded in the application's history). Monitor check type `kafka`: new messages within a window, consumer lag, stuck groups, the expected schema version. _Peek_ reads a few recent messages for troubleshooting – off unless the platform allows it, platform managers only, at most 5 messages of 4 KB, sensitive fields hidden, every read audited. Examples _Kafka – topic standards_ (with the dashboard _Kafka topics_) and _Kafka – schema change review_, and a demo cluster ([docs/KAFKA.md](docs/KAFKA.md)).
- **MQTT** (#113): a platform type _MQTT broker_ (mqtt, mqtts, ws, wss; password or client certificate) and the monitor check type `mqtt`: messages on a topic or pattern within a window, devices that went silent (every topic of a pattern), connected clients. One listening connection per broker in use keeps per topic only when the last message came and how many – never the content (table `mqtt_topics`, migration `ops-010-mqtt-topics`, additive). A demo broker over WebSocket ([docs/MQTT.md](docs/MQTT.md)).
- Processes see what Steward read from a component's platform (Kubernetes namespace, repository, Kafka topic) as `readout` of the components of an application input.

### Fixed

- The CheckMk trend example's test depended on the time of day: the demo `/var` series now grows 0.8 % a day, far enough from the 14-day warning.

## [0.2.6] - 2026-10-30

Steward follows slow signals and reads more of the monitoring around it. Every dataset metric gets a robust **trend line**: KPIs show the change of the trend and when a limit is reached at this rate, checks use `$trend` and `$daysUntil`, and the daily summary lists limits reached soon. **CheckMk** and **Prometheus** become monitor check types – the current state of a host or service, a PromQL query against WARN and CRIT levels with the worst series named – and availability objectives can take their figures from PromQL. **Kubernetes** namespaces of applications are read with a read-only service account: deployments, the images as tech stack entries for the end-of-life checks, pods that are not well and cert-manager certificates, plus a monitor check. Monitors post **Teams cards** to their own channels, and systems get their own end-of-life messages. Three database migrations, all additive: `ops-008-metric-limits`, `ops-009-prom-objective-readings` and `catalogue-006-namespace-cluster`.

### Added

- **Trends and forecasts on metrics** (#145): a robust trend line (Theil–Sen, counter resets followed, too few points said plainly, stable or rough) for every dataset metric. KPIs show the change of the trend line and what it is based on, and when a limit is reached at this rate; trend widgets can draw dashed trend lines. The publish step takes `limits` and `floors` per metric, a KPI its own limit. Checks use `$trend('dataset/metric', '7d')` and `$daysUntil('dataset/metric')`; the daily summary gets a _Trends_ section (limits within 30 days, strong changes); `GET /api/v1/datasets/{key}/metrics?trend=7d` returns `trend`, `limit` and `forecast`. Migration `ops-008-metric-limits` (additive).
- **CheckMk** (#130): monitor check type `checkmk` – the current state of a host or service (OK / WARN / CRIT / UNKNOWN → up / degraded / down / unknown, the plugin output as message), one shared read per site and cycle. Platform type _CheckMk (monitoring)_ with an automation user and a connection test, a demo site, and the example process _CheckMk – trend summary_ with the dashboard _CheckMk trends_: averages, peaks, time above WARN/CRIT, week-on-week change and days until CRIT, checks for levels crossed and series heading for CRIT, a morning report. Alerting on raw metrics stays in CheckMk ([docs/CHECKMK.md](docs/CHECKMK.md)).
- **Prometheus** (#110): monitor check type `prometheus` – a PromQL query against WARN and CRIT levels (above or below), every series judged and the worst one named, no data unknown by default – and a platform type _Prometheus (PromQL)_ for Prometheus, Thanos, Mimir and VictoriaMetrics with a connection test and a demo. Availability objectives can take their figures from a PromQL query with `$window` (read hourly per window; with several series the lowest counts). Migration `ops-009-prom-objective-readings` (additive).
- **Kubernetes** (#111): a platform type _Kubernetes cluster (read-only)_ with a read-only service account (role in [docs/KUBERNETES.md](docs/KUBERNETES.md)). Application components of type _Kubernetes namespace_ name their cluster; Steward reads their deployments with ready replicas and images, pods that are not well and cert-manager certificates every 6 hours or on _Read now_. Images become tech stack entries (source _read from the cluster_; a built-in image → product list that administrators extend with their own images; unmapped images are listed, not guessed), so end-of-life checks cover them. Monitor check type `kubernetes` (deployments ready, no pod crash-looping), the example _Kubernetes – namespace health_ with the dashboard _Kubernetes_, and a demo cluster. Migration `catalogue-006-namespace-cluster` (additive).
- **End of life for systems** (#129 follow-up): the people responsible for a system get the end-of-life messages of its tech stack, also for systems no application runs on yet (audited as `system.eol_notice_sent`). The example _End of life – tech stack overview_ and its dashboard now list systems too – per application and environment, and systems no application uses – so applications whose stack is only on their systems show up. New expression function `$systems()`.
- **Teams cards for webhooks** (#130): monitor webhook outputs and the notification webhook take the format _Teams card_ (an Adaptive Card in the configured look). The new platform type _Microsoft Teams channel (Workflows)_ keeps the Workflows URL as an encrypted credential (a Teams card always goes to such a platform, never to a URL in the monitor definition), so each monitor or team posts to its own channel.

## [0.2.5] - 2026-10-30

The service catalogue learns what applications run on: **systems** with their own tech stack, per environment, and an ordered list of environments. Credentials can belong to applications, components and systems, owners are picked from the users and teams, and tags take a value (`env=prod`) and filter lists. **Maintenance windows** – once or repeating – keep affected monitors quiet, can pause run messages, hold back objective breach messages and tell the owners in advance, with a calendar and .ics files. **Incident reviews** record what happened with a timeline prefilled from what Steward saw, and track their measures with owners, due dates and reminders. Four database migrations, all additive: `catalogue-004-systems`, `credentials-003-belongs-to`, `catalogue-005-maintenance` and `records-005-measures`.

### Added

- **Systems** (#129): servers, VMs, clusters, appliances and cloud services that applications run on, kept once under _Service management → Systems_ – with vendor or provider, CMDB link, owners, note, their own tech stack (by hand or from an SBOM) and optionally the Steward platform they are. Applications **run on** systems per environment; the application page groups them by environment, the system page lists its applications. The application's tech stack, the end-of-life messages (production first, `db01 (prod)`) and the scorecard part _Tech stack_ include systems. API v1: `/systems`, `/systems/{systemId}`, `/environments`.
- **Environments** (#129): _Settings → Environments_ keeps an ordered list (name, colour, production), offered on platforms, "runs on" links and components; other values stay possible and values in use can be adopted. Components get an optional environment (empty: all environments) and the components table filters by it. The process input types _Application_ and _Applications_ return `systems` and `environment` on each component.
- **Credentials that belong to the catalogue** (#143): an entry of the credentials register belongs to an application, a component or a system – the platform stays optional, so applications without an API in Steward document their technical users, keys and certificates too. New entries take the owners of what they belong to; the application page lists the entries of the application and its components, the system page those of the system. Filter `belongs` in the list and in API v1 (`belongsTo` on every entry), CSV column `belongs_to`.
- **Owner picker** (#143): owners of services, applications, systems and duties are picked from the users and teams (with avatars), like the owners of credentials and the responsibles of tickets already were. The server refuses users and teams that do not exist (`USER_UNKNOWN`, `TEAM_UNKNOWN`); owners stored before stay valid. A renamed team stays the owner, responsible, recipient and access-list entry everywhere; a deleted team leaves owner, responsible and recipient lists, while access lists keep the entry so that access never widens. Before a team is deleted or an account deactivated, the Users page lists where it is still named (`GET /api/users/{id}/references`, `/api/teams/{id}/references`).
- **Tags with a value** (#143): tags are `key` or `key=value` (shown as `env: prod`) on services, applications, processes, monitors, records and credentials. The tag input takes a key, Tab moves to the value, Enter adds it; keys and values are suggested from the tags in use. Clicking a tag filters the list (`?tag=env=prod`, or `?tag=env` for every value); the public API filters the same way and now also on services, applications and credentials. Existing tags stay as keys.
- **Maintenance windows** (#108): plan work on platforms, systems, applications and services under _Service management → Maintenance_ (list and month calendar) – once, or weekly or monthly with an optional end, in the instance's time zone. While a window lasts, monitors that check an affected platform show _maintenance_ and send no alerts, check and run messages of runs on those platforms can go to the app only, and availability objectives of affected services record breaches without a message. Objectives show the planned minutes per window next to Gatus' figures, which stay unchanged. The responsible people and the owners of what it reaches are told when it is planned, before each occurrence, when it starts and when it ends (event `maintenance.announced`). Each window offers a calendar file (.ics) and can name its change record; platform, system, application and service pages show the maintenance going on and coming up. API v1: `/maintenance-windows`.
- **Incident reviews** (#109): a built-in record type (`PIR`) for post-incident reviews on the decision workflow – incident window, severity, impact and cause as fields, summary, timeline and learnings in the text. Start one from a resolved ticket reference (its time, title and services), from a monitor outage, or on its own. _Fill in the timeline_ offers what Steward saw in the window – monitor changes, failed runs, ticket events and, for administrators and auditors, audit entries, only what the author may see – and copies the ticked entries into the text. **Measures** with owners and due dates are tracked like duties: reminders before and on the due date and weekly while overdue (event `measure.due`), open measures on the service page, still editable after the review was accepted. API v1: `/measures`.
- Migration `credentials-003-belongs-to` (additive: columns `credentials.belongs_kind`, `belongs_id`).
- Migration `catalogue-004-systems` (additive: tables `systems`, `system_stack`, `application_systems`, column `application_components.environment`).
- Migration `records-005-measures` (additive: tables `record_measures`, `record_measure_reminders`).
- Migration `catalogue-005-maintenance` (additive: tables `maintenance_windows`, `maintenance_targets`, `maintenance_notices`).

### Changed

- The record type of the Git sync example is now `RCA` (_Root cause analysis_): `PIR` is the key of the built-in incident review type. An installation that already has a type `PIR` (synced from Git or created by hand) keeps it; the built-in type then gets the key `IR`.

## [0.2.4] - 2026-10-29

Automated runs get one notification policy – schedules, webhook triggers and monitor outputs decide when and where failed checks notify, what counts as a change, and can pause their messages – and the messages say what is wrong, which way it changed and what to do. A dataset keeps one partition per source platform, so the same process run against several tenants no longer overwrites the others, and dashboards filter by source. The monitor editor keeps cards apart and validates while you type, the run dialog offers one run mode, failed checks on the start page are grouped, and the tenant usage example reads the real Usage Transparency API. Four database migrations, all additive: `ops-005-run-retention-default`, `ops-006-notify-policy`, `triggers-002-notify-policy` and `ops-007-dataset-sources`.

### Added

- **Datasets per source platform** (#142): a dataset keeps one partition per source – the platform its rows were read from (the only connection, the publish step's new `source` connection, or all bound platforms; the instance without connections). A run replaces only its own partition, so the same process scheduled against several tenants no longer overwrites the others; rows carry `_source`, metrics are kept per source. Dashboards get a _Sources_ filter (in the URL, remembered per person) that every widget follows or pins, a _Source_ column in tables, one line per source in trends, a value per source in KPIs and freshness per source. A partition whose platform has an access list without the reader is hidden (administrators and auditors see all). ### Security

- **Availability objectives only name Gatus platforms their author may see** (#86): an unknown or hidden platform is "not found" (no probing of platform ids), and readers who may not see the platform get an objective's status and values but neither the platform nor the endpoint. Documents a reader may not read do not count on the scorecard, also not in the stored daily history (shown as hidden). The scorecard cannot be cleaned by removing history: objectives are archived, never deleted (samples and breaches stay; an archived objective counts with its last status until its longest window has passed), and a duty archived during its current period counts until that period ends. An objective without data for more than 24 hours needs attention (a source turned off or an always-up endpoint chosen to hide a problem shows), breach messages are limited to one per objective a day, and the migration dry run refuses scorecard rows out of range.
- **Exceptions of service duties need a second person** (#85): skipping a period of a duty is a four-eyes decision – the requester (also under a former name of an imported account) can never approve it; administrators, designers and the duty's and the service's owners as they were when it was asked for can (an owner added afterwards cannot, so the requester cannot pick the second person), and they are notified (`duty.exception`). Exceptions reach at most three periods ahead, and the duty shows how many are planned. Before a duty is archived or its process, interval, grace period or level change, its open periods are closed under the old rules, so nobody can erase or re-judge them: a current period without a run that counts is recorded as _ended without a run_ (not met, like missed; stored under its key with a suffix, `2026-10~1`, and for mandatory and recommended duties the owners get the new message `duty.ended`, not the person who made the change), and the new rules start at the moment of the change – no run from before it counts, and no past period is judged again. A change that only makes a duty stricter (a higher level, a shorter grace period) applies to the current period, which stays open. It is not a step-up: it changes no rights or secrets, and both people, the reason and the decision are in the audit log. Duties only name processes their author may view, and people who may not view the process see the status but neither its name nor its runs.
- **Evidence files of manual steps** (#83) are handled like record attachments: allow-listed types whose content must match, at most 20 files of 20 MB per step, written once and read-only with their SHA-256 (a changed file is refused), always downloaded as attachments with a sandbox CSP. Only the person working on the step adds or removes them, and only while the step is being worked on (checked again when an upload finishes); an entry's files are fixed when it is completed. Whoever may see the run reads them. A migration package checks their paths and content again. Verification rights are checked on the server and never let the person who completed a step, or anyone who added evidence to it, verify it, also not under a former name of a moved instance.
- **Mapping a platform to an application needs the manage right on the platform** (#84 review): the mapping decides which application – and whose CIA rating – a platform's evidence pack names, so an application owner who only uses a platform can no longer claim it (or remove it).
- **Protection needs show what they leave out, and say why they moved** (#84 review): a service lists the applications it does not count (archived, not rated, needing re-rating), and every change of an application, of the members or of the scale that moves a service's effective protection need writes `service.protection_need_changed` on that service. A document scoped to an application is also recorded on the application.
- **CIA scale changes that re-order levels, or swap their labels, need a confirmation and flag the ratings** (#84 review); stored scales are validated like a save (an invalid one falls back to the BSI default, every protection need and rating says it is not reliable – UI, public API, evidence packs – and ratings and overrides are refused until an administrator saves a scale; a migration package with one is refused in the dry run).
- **Changing the CIA scale asks for a step-up** (#84): `PUT /api/catalogue/cia-scale` (administrators) maps or flags the ratings of every application at once, so it needs a fresh confirmation like other bulk changes. Ratings, overrides and document scopes are everyday catalogue changes by the people responsible: audited, without a step-up.
- **Sensitive actions ask for a fresh confirmation** (#14): a stolen or unattended session can no longer create API tokens, grant roles, add team members, give anyone a right in an access list (a new or raised entry, the role defaults of an emptied list, a new owner), reset passwords, export the audit log, the credential register or evidence packs, or change single sign-on, sign-in, outbound, notification delivery (SMTP server, webhook URLs, e-mail domains) or audit anchoring settings without the password or a fresh sign-in at the identity provider. The stored SMTP password is never sent to another server: changing the server, port or user, or turning TLS off, needs it again (`SMTP_PASSWORD_AGAIN`). API tokens can no longer use `GET /api/audit/export` and `GET /api/credentials/export.csv`. Single sign-on providers that send no `auth_time` cannot confirm (Entra ID: add the optional claim `auth_time`), see [docs/SSO.md](docs/SSO.md#step-up-re-authentication).
- **Single sign-on claims, hardened after review** (#77): _lower case without @domain_ strips only the domains the provider lists (required) and refuses user names of any other domain, so `boss@evil.example` cannot claim `boss`; a stable identifier must include `sub` or `oid` or custom claims the administrator confirms as unique per person (the confirmed claims are stored and audited, and the confirmation holds only for exactly those claims) – claims many people share (`tid`, `groups`, `roles`, `hd` …, also nested or in another case) are refused (`SSO_STABLE_ID_NOT_UNIQUE`); numbers and strings never give the same link; identifier values are taken exactly as sent (no trimming, joining or cutting; lists, objects and oversized values are refused); the recorded issuer + `sub` changes only when an identity is linked, never at a plain sign-in; user names are NFKC-normalised and limited to letters, digits and `. _ @ + -` when they link an account by name or create one (identities linked already keep signing in); a name that keeps a domain after stripping one is refused; group overage is checked for the configured claim only; `email_verified` comes from the same source as the e-mail address; long (hashed) links survive a kept issuer change; linking a local account ends its sessions; a refused sign-in shows the person only a reference (`SSO_SIGN_IN_REFUSED`) – the reason is in the audit entry; the sign-in page no longer reads accounts.
- **Linking existing accounts at the first single sign-on is a setting per provider** (#77): _only accounts an administrator bound to this provider_ (the default for new providers), _any local account with the same user name_ (what earlier versions did – providers saved before keep it, and the editor warns) or _never_. `email_verified` is now required whenever the e-mail claim names or identifies an account (also with `usernameClaim: 'email'`), unless the provider is marked as verifying every address. Links name the issuer: when a provider's issuer changes, links from before are tied to the former issuer (a person at the new issuer with the same `sub` cannot take the account over) unless the administrator keeps them. An account linked by the configured stable identifier claims is never re-linked to another identity. Group overage indicators (Entra `_claim_names`/`_claim_sources`, `hasgroups`) never grant roles and are logged and audited (`sso.groups_overage`). The editor warns about claims people or other tenants can influence (`email`, `upn`, `preferred_username` with multi-tenant issuers, `name`), a multi-tenant issuer without a required `tid`, Google without `hd`, and stripped domains; every change of the claim settings is audited with the former values. Fields the provider keeps in sync can no longer be changed by an administrator either. Claim values are bounded and control characters removed; the test sign-in never returns tokens or the client secret and is visible only to the administrator who started it.
- **zod 4 with a length limit on every list** (#63, [GHSA-mrhx-c7xc-m3w5](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5) / CVE-2023-54404): zod is upgraded from 3.25 to 4.6.7, which stops at a list's maximum length before it checks any item. - Adding a documentation link to a platform with a URL that can't be parsed answered `500` instead of `400`.

- **Stored files and logos are served with the type of their content**, never with the type a database row (or an imported package) names: run artifacts are shown inline only when they are PNG, JPEG, GIF or WebP images, anything else is a download (`application/octet-stream`, `Content-Security-Policy: sandbox`, `nosniff`); a record attachment of a type uploads never produce is a plain download; the header logo and the report logo take their type from their bytes. ## [0.1.1] - 2026-10-23

Safe in-place updates, living documents for service documentation, and security fixes (some also affect v0.1.0 installations – updating is recommended).

### Added

- **Safe in-place updates** ([docs/INSTALL.md](docs/INSTALL.md#6-updating)): before an update migrates an existing SQLite database, Steward writes a consistent copy to `<data folder>/backups/pre-<version>-<UTC time>.db` (0600; the newest 3 are kept, `SM_UPGRADE_BACKUPS` changes the number, `0` turns it off). Nothing is copied when there is nothing to migrate or for a new database. A failed migration stops the start with a message that names the migration and the copy. After the vault is unlocked, the audit log gets one `system.upgraded` entry (old and new version and schema, migrations applied, path of the copy). PostgreSQL is not copied by the app: the log recommends `pg_dump` before updates. `db:copy` keeps such a copy of an older SQLite source as well. The database is now opened (and migrated) before the server listens.
- **Upgrade test from real v0.1.0 data**: `server/test/upgrade.test.ts` starts the current version on a data folder written by v0.1.0 (`server/test/fixtures/upgrade/v0.1.0`, test data with a published passphrase) – on SQLite, and on PostgreSQL after `db:copy` – and checks migrations, vault unlock, the old data, audit chain and signed checkpoints, resuming a waiting run, attachments, the PDF report and the evidence pack. `scripts/fixtures/make-upgrade-fixture.mjs` makes the fixture for each new minor release ([docs/TESTING.md](docs/TESTING.md#upgrade-tests)).
- **Living documents** (#56): a record workflow `document` and the built-in type `DOC – Service documentation` (also added to existing installations; `SDOC` when `DOC` is taken) for operations manuals, IAM and authorization concepts. Approving freezes the content as an **edition** (1.0, 1.1, 2.0 – minor or major, chosen at submit, with a required change summary; four-eyes as for other approvals, per edition). _New edition_ drafts the next one while the current edition stays valid; _Withdraw_ (with a reason, optionally naming the replacing document). The document page has a **changelog** (editions and reviews, open a frozen edition, diff to the previous one, PDF per edition); the record PDF gets a _Document control_ section. **Periodic reviews**: interval per type (default 12 months) and document, review owner, an earlier date; status current / due soon / overdue with the credentials reminder settings; _Reviewed – no change_ and _Needs update_; reminders to the review owner (event _Document review due_). Shown in the records list (workflow and review filters), the start page tile _Reviews due_, the daily summary, the scheduled report's records section, links (current edition), the control mapping and evidence packs (edition, hash, approval, last review), and read-only in `/api/v1` (`/records/{id}/editions`, `/editions/{edition}`, `/reviews`). New audit actions `record.edition_approved`, `record.withdraw`, `record.reviewed`, `record.review_settings_changed`, `record.review_reminder_sent`. Reviews cannot be weakened by the people who write a document: the review owner and the document's own interval need an approver (no reviews or an interval longer than the type's an administrator; an approver who wrote the document cannot become its review owner), editors and the owner may only set an earlier date, and _Reviewed – no change_ is refused while a review's update request is open. Editions and reviews cannot be changed or deleted in the database (triggers), and are checked with their metadata (change summary, authors, approver, dates) against the authentic audit entries. See [docs/RECORDS.md](docs/RECORDS.md#living-documents).

### Changed

- Code scanning no longer shows Semgrep findings that are suppressed in the code with a reason (`nosemgrep … -- reason`); the CI job already ignored them, but the uploaded SARIF still contained them, so code scanning opened alerts.
- Dependabot proposes new versions after 14 days (major versions after 21) instead of 7 and 14, matching the rule that dependencies are at least two weeks old. The Mantine packages and Vite with its React plugin come as one pull request each, since they must be upgraded together. Major versions of `@types/node` are ignored: the types follow the oldest supported Node.js version (24). Security updates are not delayed.

### Security

- **Request body limits against memory exhaustion in validation** ([GHSA-mrhx-c7xc-m3w5](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5), zod): a signed-in user could crash the server with one large request – a list of 12 million items in a 23 MB body made validation allocate 3 GB. Every JSON body is now checked before validation: at most 10,000 items in one list, 10,000 fields in one object, 200,000 values and 100 levels (imports of bundles, connector types and monitors: 50,000 and 1,000,000); above that `413` with `BODY_TOO_COMPLEX`. Requests without a sign-in must give a `Content-Length` (a chunked body skipped the 64 KB limit). See [docs/SECURITY-HARDENING.md](docs/SECURITY-HARDENING.md#request-body-limits).
- **"Superseded by" named records the reader may not read.** The record page, `GET /api/v1/records/{id}` and the record PDF showed the id, number and title of the superseding record (decisions; replaced living documents) even when the reader may not read it, e.g. an access change entry. It now shows as not visible, like links to hidden items (`supersededBy.visible: false` without id, number or title). A decision can only be superseded by a decision record, and a document only replaced by a living document.
- **No owner hand-over while an approval is pending.** Four-eyes compares the approver with the current owner, so the owner of a submitted change request (or a proposed decision, a documented access change) could hand it over to someone else and approve it. Changing the owner is now refused (`RECORD_OWNER_LOCKED`) until the decision.
- **Approvals name the content they decide on.** The transition API takes an optional `contentHash`; the web app sends the hash it shows in the approval dialog, and Steward refuses the decision (`RECORD_CHANGED`) if the record was reworked and submitted again in the meantime.
- **Request rate limits** for the web app's API, the inbound webhooks and the web UI's files ([@fastify/rate-limit](https://github.com/fastify/fastify-rate-limit)): 600 requests per minute and signed-in user, or per client address without a valid sign-in (`SM_RATE_LIMIT_PER_MINUTE`, `0` = off). Counted after the session check, so made-up session cookies or tokens count against the address, including refused (401) requests. Lower limits of their own for expensive actions: 30 per minute for PDF reports, evidence packs, exports, imports and audit verification, 120 for starting runs, checks and platform tests, 10 for password and passphrase changes; webhooks and the web UI's files get a bucket of 10 times the general limit per address. Above a limit: `429` with `Retry-After`, `RateLimit-*` headers and the error code `RATE_LIMITED` (translated in the web app), and one log line per user or address and minute. Health and readiness probes, `/api/v1` and `/api/mcp` (own limiters) are not counted. Counters are in memory, per server process. See [docs/SECURITY-HARDENING.md](docs/SECURITY-HARDENING.md#request-rate-limits).
- Regular-expression denial of service: an administrator uploading a header logo that starts with `<!--` followed by a few hundred `--><!--` blocked the server for minutes (the SVG detection regex backtracked exponentially), and a Markdown link like `[a](` followed by many spaces or tabs took seconds to minutes to render (records, notes, report text – on the server and in the browser). Both are now linear scans. (CodeQL `js/redos`, `js/polynomial-redos`)
- Files in the data folder (run screenshots, PDF reports, platform documents) and the monitor examples are opened through one helper that only accepts plain names and refuses any path outside its folder. The ids were already looked up in the database first, so this is defence in depth.
- Traces (OpenTelemetry, off by default) carry the user as a keyed hash with a per-installation key instead of a plain SHA-256 of the user name, so whoever holds the traces cannot re-identify users by hashing known names.
- CodeQL no longer scans test code (`server/test`, `e2e`), which is not shipped; everything else, including the demo mock servers, still runs with the `security-extended` queries.

### Fixed

- `GET /api/runs` returns a full page (up to `limit`) even when many runs belong to processes the user may not see; before, a page could end early and look like the end of the list.
- **Node.js 26: crash after a few minutes** (`Check failed: IsCompatibleCode` in `Genesis::InitializeGlobal_regexp_linear_flag`, exit code 133): the expression engine switched V8's experimental regexp engine on with `v8.setFlagsFromString()` while running, which Node documents as undefined behaviour; every worker thread started later (the regular expression guard, the PostgreSQL bridge) then built its context with the flag, and Node 26 aborted there. Steward no longer changes V8 flags at runtime (an ESLint rule and a test keep it that way) and needs no V8 flag at all: regular expressions in process expressions run natively only when they are fixed-length (no quantifier, alternation, back reference or lookaround – bounded work); all others run in the worker thread with its time limit, which now returns a batch of matches per round trip. A catastrophic pattern such as `/(a+)+$/` now fails after 500 ms with "simplify it" instead of being rescued by the linear engine. Node.js 26 is supported and tested in CI next to Node.js 24 (LTS, the primary version); `engines` is `^24.0.0 || ^26.0.0`.
- **German UI** – everything is translated now, also on the _Dokumente_ pages:

Zod validation errors are shown inside a translated sentence;
  - the four-eyes and other reasons why a record action is not possible (`reasonCode`), the errors and notes of the Markdown import (`errorCode`, `warningCodes`) and why a task cannot be decided (`cannotDecideCode`);
  - the built-in record types: description, Markdown template, field labels and help, select options (_niedrig/mittel/hoch_) in the web UI, the record PDF and the records section of scheduled reports – as long as an administrator has not changed them. New records start with the template in the UI language (API/MCP: in the creator's profile language);
  - a few hard-coded English texts (task panel, report language names, close buttons of dialogs, the default name of a new sign-in provider) and German texts that were still English (_Protokoll_, _Audit-Log_, _Anfrageinhalt_, …); dates and numbers in the theme settings follow the UI language;
  - the PDF of a record is generated in the requester's profile language when the request names none (was English).
- New checks: `npm run i18n:literals` finds texts in the web UI that do not go through `t()`; `npm run i18n:check` also reports texts that are still English (allow-list `scripts/i18n-allow.json`); both run in CI. ### Security

- Expressions: regular expressions such as `/\u{0,99}X/` (without the `u` flag `\u{…}` is a letter with a quantifier) were classed as fixed-length and ran on the main thread, where a crafted pattern could block the server; they now run in the time-limited worker like every other quantified pattern.

- Regular expressions that relied on the V8 linear-engine fallback (see _Fixed_) work in linear time without it: the JSON Web Token mask of error reports (was quadratic on long `-eyJ-eyJ…` runs) and the Prometheus value parser of the Gatus metrics scraper (quadratic on long digit runs). Error-report scrubbing caps every string at 8 192 characters before its patterns run (known secrets are still removed from the whole string first), so no string takes more than about a second.
- Git sync review fixes: the _Updates from Git_ inbox hides updates of processes and monitors the reviewer cannot see (no name, no current definition; detail, accept and reject answer 404); blobs of SHA-256 repositories are checked against their object ids too; _Require signed commits_ checks every new commit since the last fetched commit through the hosts' compare/commits APIs (not only the branch head), refuses the whole fetch if one is unverified (nothing staged, audited) and can be limited to allowed signers (logins or e-mail addresses); superseded updates are deleted and the content of rejected ones removed after 30 days; one `sync.fetched` audit entry per fetch lists the staged files instead of one entry per file.
- Git sync: repository hosts must pass the outbound policy; the access token is vault-encrypted, never returned and only sent to the source's API base (redirects refused); responses are size-capped, blobs checked against their Git object ids, paths confined to the folder, YAML parsed as plain data, files with secret-looking values refused; optional signed-commit requirement; source configuration needs a signed-in session; the push webhook is HMAC/secret-authenticated and rate-limited; every fetch, staging and decision is audited.
- Evidence packs only contain what the requester may see (the audit log excerpt only for auditors and administrators), are size-limited, written to disk as they are built and deleted after the retention period; requesting, building and downloading them is audited.
- Access governance (review round 3, see [docs/COMPLIANCE.md](docs/COMPLIANCE.md)):
  - Access change entries are written and documented only by people who may use the platform, and read only by administrators, auditors, approvers, their owner and who has a right on the platform – also in record lists, search, links, backlinks, coverage, evidence packs, reports and `/api/v1`. Before, every signed-in user read them, and an operator without rights on a platform could close its reconciliation findings.
  - Nobody documents, dismisses or verifies a change of their own access (subject matched by user name or e-mail address); an entry documented by its subject does not close a finding. A finding is closed by a later entry only when the person who documents it may document the findings of the check.
  - Entries of runs name the person who started the run as performer; that person and the run's approvers cannot verify them, and nobody can change or revise them. Origin, run and finding of an entry are set only by Steward (`400 ACCESS_FIELD_RESERVED`). Entries show who documented them and who last edited them; entries changed in the database are flagged (`tampered`) and do not count.
  - Dataset checks need the right to view the process that publishes the dataset (when set up and on every run); the dataset key of a check with snapshots cannot change. Ignored rights are set by administrators only and audited with the old and new list (as are the recipients). Optional four-eyes dismissals (_Settings → Access reconciliation_).
  - _Verify history_ compares snapshots and findings with the authentic audit entries: deleted snapshots (also the newest), deleted findings and statuses changed in the database are reported; database triggers refuse deleting snapshots and findings.
  - Evidence packs: the offline check reports a pack signed with a key nobody confirmed as _UNTRUSTED_ and exits with 3 – pass `--public-key`, `--fingerprint` or `--trust-pack-key`; it always prints the key fingerprint. Manifest signatures are domain-separated from audit checkpoints (version 2 manifests; older packs still verify). The ZIP reader refuses bytes outside the listed entries, gaps, overlaps and local headers that differ from the central directory. Packs of someone who cannot see everything say so and count the evidence left out per control (_not visible_ instead of _gap_).
  - Mapped control items the reader may not see no longer show their id and cannot be removed by them.
  - The Insights Hub collector applies its limits while it reads the pages (rights per user, users, assignments; 16 MB per page).
  - YAML imports (control catalogues – now at most 256 KB –, processes, dashboards, monitors, API specifications, record front matter, Git sync files) are size-capped before parsing and check duplicate keys in linear time: the YAML library's own check is quadratic (40 000 keys took 20 seconds).
- Holistic review (OWASP ASVS 4.0.3 level 2), see [docs/REVIEW-2026-10.md](docs/REVIEW-2026-10.md):
  - API specifications and operations of a platform (`/api/platforms/:id/specs`, `/operations`, `/api/specs/:id/content`) were readable by every signed-in user; they now need a permission on the platform, like the platform itself.
  - API tokens can no longer manage users, teams, single sign-on providers, sign-in and outbound settings or the master passphrase (`403 SESSION_REQUIRED`): before, a leaked full-access token of an administrator could create a new administrator or reset a password and so outlive its revocation.
  - Sessions end after 30 minutes without a request and 12 hours after sign-in (before: 12 hours idle, 7 days); `SM_SESSION_IDLE_MINUTES` and `SM_SESSION_MAX_HOURS` change it. Over HTTPS the session cookie has the `__Host-` prefix (everyone signs in again once after the update).
  - Single sign-on: sign-ins in progress (started without signing in) are capped at 5000 and the return path at 1 KB – a flood of `/api/auth/oidc/:id/start` requests could exhaust the server's memory.
  - Changing the own password: at most 5 wrong current passwords per 15 minutes, each one audited (`user.password_change_failed`).
  - Webhook mapping preview only for people who may run a process; at most 100 mapped inputs and 5 s per evaluation.
  - Query strings are validated (repeated or malformed parameters gave HTTP 500, `limit=-1` unlimited lists); database errors are no longer returned to the client. Size limits for user, team, platform, schedule, task decision and process text fields.
  - Startup warnings for risky settings (no HTTPS with extra host names, demo mode on a network address, the passphrase in an environment variable, public metrics, long sessions).
  - `server/test/route-matrix.test.ts`: every route is called by every role, without credentials and with read-only and MCP tokens; a new route fails the test until its access rules are classified.
- Credentials register: no field holds a secret; free text, links and comments are checked for private keys, JWTs, well-known token formats, passwords in URLs and random-looking tokens and refused (the value is never echoed); only `http(s)` links are clickable (`javascript:`/`data:` refused); uploaded certificates are parsed and only their metadata is stored, files with a private key (PEM, DER, PKCS#12) are rejected; CSV exports are protected against formula injection.
- Gatus metrics mode: `/metrics` is unauthenticated in Gatus – the docs require it to be network-restricted. Steward fetches it through the platform and the outbound policy, only below the platform's base URL, with an 8 MB limit, a timeout and a bounded parser.
- E-mail to addresses outside Steward (credential owners, report recipients): only to allowed domains – the new setting _Settings → Notifications → Allowed e-mail domains for addresses outside Steward_ (`corp.example`, `*.corp.example`); while it is empty, the domains of the users' own addresses that an administrator, a single sign-on account or at least two users use. Checked when saving and again on every send. At most 10 addresses per credential entry and 20 per report schedule; owners who edit an entry only as its owner cannot change its owner addresses. Subjects carry user-chosen names only quoted after a fixed prefix and shortened to 80 characters.
- Report schedules: cron expressions with seconds are refused, a schedule runs at most once an hour (also schedules saved before), at most 20 schedules per owner.
- Certificate upload: PEM blocks are found in one linear pass, with at most 21 BEGIN lines (a file with many BEGIN lines without END blocked the server for seconds).
- Monitors: viewers of a monitor that includes a sub-monitor they may not view no longer see its id, key, name or check names – in root causes, _likely caused by_, the sub-monitor check, messages, history, the definition and YAML export, the `monitor.<key>` dataset, `/api/v1/monitors…`, the MCP tools and notifications ("a monitor you cannot view"). The sub-monitor check's message no longer names the monitor.
- Credentials register: the name of a linked platform is only shown to users with a right on it, and editors can only link platforms they may see (an unknown and a hidden platform get the same answer).
- Gatus metrics mode: the metrics path refuses encoded dots and slashes (`%2e`, `%2f`, `%5c`) and the resolved URL must stay below the base path; _Scrape now_ at most every 15 s per platform; deleting a platform deletes its Gatus data, and endpoints not seen for the history period are removed.
- MCP (new): its own token scope that no other API accepts (and MCP endpoints accept no other scope); `Origin` validation against DNS rebinding next to the `Host` allow-list; 64 kB request limit, no batches, strict argument schemas, per-token rate limits and time limits; tool output is structured JSON marked as untrusted data. The platform gateway is opt-in per platform, read-only (writes are refused and audited), builds paths only from the API specification or allow-listed prefixes (no absolute URLs, dot segments or encoded separators), validates query parameters, applies the outbound policy, does not follow redirects, caps responses at 512 kB, masks credentials and returns no cookies.
- Records: uploaded attachments are checked against their extension (magic numbers, e-mail headers, UTF-8 text), stored read-only with their SHA-256 (checked on download) and always downloaded as attachments in a sandbox; Markdown is rendered from a syntax tree without HTML (links: http, https and mailto only); YAML frontmatter is parsed with the core schema only (no custom tags, aliases limited) and sizes are limited; links only name targets the reader may see; a signed PDF is only accepted when its first bytes match a generated PDF of the record whose audit entry is authentic.
- Security review fixes (MCP, gateway, API v1):
  - `GET /api/v1/platforms` and `/platforms/{platformId}` only show platforms the token owner has a permission on (as the web UI does); others answer `404`;
  - the MCP stdio bridge no longer sends the token to a local URL while the data folder has no `instance.json`: it waits briefly (`--wait`), then fails; after a lost connection it checks the proof again; `--no-instance-check` (documented as less safe, with a warning) is for setups such as Docker on `localhost`;
  - credentials are masked in more encodings in run journals, logs and gateway responses: form encoding (`URLSearchParams`, e.g. `~` as `%7E`), RFC 3986 strict encoding and lowercase hex – for example a query API key echoed in a `Link` header;
  - the gateway refuses `;` in paths and path parameters (`..;/` is a dot segment for Tomcat, Jetty and Spring);
  - gateway audit entries escape control characters in client-chosen names and log invalid paths as `(invalid)`;
  - gateway rate limits apply per user and platform (not per token), and at most 2 gateway calls per platform run at the same time (`SM_MCP_GATEWAY_CONCURRENCY`), so runs and monitors keep their connection slots.
- Records (security review): the Markdown parser and the PDF engine (records, run and scheduled reports) work in linear time – unclosed brackets or emphasis, long lines of spaces, table cell bombs and very long words no longer block the server or the browser (words get invisible break opportunities, a PDF draws at most 1 000 000 characters); the Markdown import reads titles and comments without backtracking regular expressions; the signed-PDF scan reads each signature in a bounded window and a record keeps at most 100 generated and 30 signed PDFs (300 MB). Four-eyes counts everyone who attached or removed files and the authors of earlier revisions (a new revision no longer launders them). Before a transition the content hash must also match the authentic audit entry that froze the revision (a recomputed `frozen_hash` in the database is detected). The key of a record type with records cannot change any more (it is part of their content hash). Links to items the reader may not see no longer return the target id (API, UI, PDF) and `/api/backlinks` answers 404 for them; links of closed records cannot change. Signed PDFs are only accepted for the current, frozen revision and only with signature values and complete byte ranges; signer names are shown as claimed, not verified. Frozen records keep the field definitions they were approved with.
- Platform credentials are no longer sent to hosts outside the platform when a step calls an absolute URL.
- The vault rejects shortened AES-GCM authentication tags.
- Audit log integrity (review C):
  - verification fails on rows with a sequence number below 1, on rows outside the chain, and on entries removed while the server runs; the database refuses such rows (migration `security-001`);
  - every hour, on each verification and before each export a checkpoint `{seq, hash, digest, count, ts}` is signed with a per-installation Ed25519 key kept in the vault; it is written to the audit log, to `audit-anchor.json` in the data folder and as a log line for the SIEM, and can be e-mailed to auditors (_Audit log → Anchoring_);
  - verification compares the chain with these anchors and with an external checkpoint (pasted in the UI, `SM_AUDIT_ANCHOR`, `SM_AUDIT_ANCHOR_FILE`): removing the newest entries or wiping the log is detected;
  - exports include `prevHash`, details and a signed checkpoint; `npm run audit:verify-export` checks an export offline with the public key;
  - report verification, protocol seals and summary reports only trust audit entries whose HMAC and chain position check out – a forged row no longer makes a forged PDF verify;
  - audited free text is capped, failed sign-ins are summed up per account/address and minute, and entries recorded while the vault is locked are bounded (dropped entries are counted in the log); unauthenticated requests may send at most 64 KB.
- Sessions are bound to a per-session key that the web app keeps in its origin's `localStorage` and sends as `x-sm-session`; a session cookie received by another program on the same host no longer signs anyone in. Download links carry a read-only link key. **Everyone has to sign in again after the update.**
- The master passphrase can be read from a file (`SM_MASTER_PASSPHRASE_FILE`: Docker secrets, systemd credentials); both passphrase variables are removed from the environment at start. Browser steps start Chromium with a minimal environment and with its sandbox (unless running as root); the desktop launcher starts the user's browser without `SM_*` variables or secrets.
- Vault format 2: random data, audit, integrity and signing keys wrapped with a scrypt key (N=2^17); existing vaults are converted on their first unlock (the audit chain stays valid). Administrators can change the master passphrase (_Settings_), optionally rotating the data key; new passphrases need 12 characters; wrong passphrases are audited and throttled.
- Platform connection settings (base URL, authentication, token URL, trusted origins, headers) and sign-in provider settings are sealed with an HMAC; when they are changed directly in the database, no requests are sent until an administrator confirms them.
- Password checks run off the event loop with a concurrency limit and the same cost for unknown user names.
- The desktop launcher only opens its window for a server that proves it knows the secret in the user's data folder (port squatters are refused).
- Data folder `0700`, database, vault and key files `0600` on Linux/macOS (existing installations are fixed at start).
- Audit CSV export escapes cells that spreadsheets would run as formulas.
- `SM_TRUST_PROXY` for reverse proxies (real client addresses for the audit log, lockouts and webhook CIDRs); `Secure` cookie and HSTS with an `https://` `SM_PUBLIC_URL`.
- Failed sign-ins with user names that belong to no account store a pseudonym instead of the typed text; new process input type _secret_ (stored encrypted, `***` everywhere).
- Redaction of JSON-/URL-/Base64-encoded secrets, Basic credentials and OAuth token fields in run data; error reports scrub encoded secrets; traces carry a user pseudonym and scrubbed exception messages; TLS 1.2+ with forward-secret ciphers; `Cache-Control: no-store` on API responses; the desktop executable re-checks its unpacked files at every start; hardened compose files.
- Supply chain: `npm ci --ignore-scripts` plus an enforced install-script allow-list in CI, release builds and the Dockerfile; signed build provenance and SBOM attestations for release archives and the container image.
- New: [docs/SECURITY-HARDENING.md](docs/SECURITY-HARDENING.md) (checklist for a work deployment) and [docs/PRIVACY.md](docs/PRIVACY.md).
- Every process expression now runs under guard rails by default — a time limit (`SM_EXPR_TIMEOUT_MS`, default 5 s), stack-depth and sequence-size limits (`SM_EXPR_MAX_DEPTH`, `SM_EXPR_MAX_SEQUENCE`), a heap watchdog and regular expressions that cannot backtrack catastrophically — and long evaluations yield to the event loop, so a single expression can no longer freeze the server (DoS).
- Resolved secret values (`$secret()` and platform credentials) may only leave Steward towards the platform's own allowed origins: outbound requests are scanned for any bound platform's secret (also base64/URL-encoded) and the step fails if one would reach another origin. Secrets are masked in their encoded forms in logs too.
- Credentials are re-evaluated on each redirect hop: custom-named API-key headers, default headers and any header carrying a secret are dropped when a redirect leaves the allowed origins, and `https → http` downgrades that would carry credentials are refused (redirects are followed manually, max 5 hops).
- New outbound destination policy (SSRF protection) for process-controlled requests — `http` node, pagination, browser navigation and sub-requests, OpenAPI import by URL — configurable under _Settings → Outbound access_ (`platforms` / `allowList` / `open`, `SM_OUTBOUND_POLICY`). Cloud-metadata and link-local addresses and the server's own API port are always blocked, and the resolved IP is pinned for the connection (no DNS rebinding).
- Dashboard datasets are owned by the process that first publishes a key; another process can no longer overwrite it or hijack its dashboard visibility.
- Dry runs can be made read-only for a browser step (`dryRunReadOnly`), and a dry run now warns in the protocol when a browser step performs page interactions that could change data.
- Monitors adopt the same policies: http/tcp/ping checks and webhook/Zabbix outputs are subject to the outbound policy (DNS-pinned; raw `host:port` checks need an explicit allow-list entry such as an IP/CIDR and are not inferred from platform origins); monitor http checks follow redirects manually and drop custom headers cross-origin; check error messages no longer echo the upstream response body; the guarded expression evaluation bounds condition/heartbeat/freshness expressions (CPU, memory via a `$pad` cap, and regex time); and gateway heartbeat batches share a global evaluation-concurrency cap (`SM_MONITOR_EVAL_CONCURRENCY`).
- Semgrep findings triaged (all rule sets of the CI job, see [docs/SECURITY-PIPELINE.md](docs/SECURITY-PIPELINE.md#semgrep-triage)): the dev, PostgreSQL-test and install-script helpers start npm without a shell, also on Windows (`scripts/npm-command.mjs`); monitor-gateway key patterns (glob) and the API path editor match without regular expressions built from configured data; translation lookups ignore inherited properties; the CI gate also blocks HIGH/CRITICAL findings; SARIF uploads get the `actions: read` permission they need.
