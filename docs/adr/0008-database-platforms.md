# 0008. Database platforms: direct SQL, read-only

- **Status:** Accepted
- **Date:** 2026-11-05
- **Since:** 0.7.0 (#203, step 1: PostgreSQL, MariaDB/MySQL, SQL Server)

## Context

Access reviews, account hygiene, monitor checks and datasets are needed for the databases services run on, not only for the platforms in front of them. Until now every platform Steward _sends requests to_ speaks HTTP (Kafka and MQTT are read through their own clients, but only for fixed reads Steward chose). A database platform is the first platform kind whose requests are written by the people who design processes: a SQL statement. That needs the same evidence and safety rules as an API call – credentials only from the vault, the outbound policy, audit, dry and test runs – and one more rule HTTP does not need: a statement must not change the database, whatever it says.

## Decision

**One platform kind `database`, one driver per DBMS.** The connection settings are `config.database` (`shared/src/database.ts`): `dialect` (`postgresql`, `mysql` for MariaDB and MySQL, `sqlserver`), `host`, `port`, `database` (for Oracle later: the service name), `tls` (`verify` – the default – with an optional CA, `require` without verification, `off`), the platform's limits and the pool size. They are sealed with the other connection settings and change only through `PUT /api/platforms/:id/database` (the platform's _manage_ right, audited as `platform.database_changed`), like the AI settings of an LLM gateway. User name and password are credentials of the platform (vault keys `username`, `password`). The settings have room for later sign-ins (`auth: password` now; Entra ID tokens for SQL Server and IAM tokens for RDS later) without a migration.

**Drivers are pure JavaScript** and loaded only when a database platform is used: `pg` (a dependency already), `mysql2`, `tedious`. A driver (`server/src/dbms/<dialect>.ts`) implements one small interface (`server/src/dbms/types.ts`): `connect(target)` returns a connection with `run(statement, limits, signal)` and `close()`. Oracle (`oracledb` in thin mode, `SET TRANSACTION READ ONLY`) is a later step and fits the same interface.

**Read-only, enforced in three layers.** No layer is trusted alone:

1. **The database account** is read-only. [DATABASES.md](../DATABASES.md) gives the exact `GRANT` statements of a least-privilege role per DBMS; the connection test reports when the account can write.
2. **The session.** Every statement runs in a transaction that is always rolled back:
   - PostgreSQL: the session starts with `default_transaction_read_only=on`; each statement runs in `BEGIN TRANSACTION READ ONLY`, through a cursor (`DECLARE … NO SCROLL CURSOR FOR`, which PostgreSQL accepts for queries only and refuses for data-modifying `WITH`), in the extended protocol (one statement per message, enforced by the server), then `ROLLBACK`.
   - MariaDB/MySQL: `SET SESSION TRANSACTION READ ONLY`, then `START TRANSACTION READ ONLY`, the statement as a server-side prepared statement (one statement; `multipleStatements` stays off), then `ROLLBACK`. Writes to temporary tables are still possible in MySQL's read-only transactions – the statement check refuses them.
   - SQL Server has no read-only transaction. Each statement runs in `BEGIN TRANSACTION … ROLLBACK`, and the account must be read-only (`db_datareader`, `VIEW SERVER STATE`, `VIEW ANY DEFINITION`, nothing else). This is the weakest of the three; the documentation says so.
3. **The statement check** (`shared/src/sqlcheck.ts`, the same in the editor and on the server): conservative and parser-free, a **best-effort extra layer** – a denylist cannot be complete, the read-only account is the real protection. It splits the text into literals, quoted identifiers, comments and words and refuses: anything but one `SELECT` or `WITH … SELECT`; a `;` before the end; words that start or change something (`INSERT`, `UPDATE`, `DELETE`, `MERGE`, `EXEC`, `INTO`, `SET`, `LOCK`, `OPENROWSET`, `NEXT VALUE FOR` …); for SQL Server, whose batches need no semicolons, also the words that start control flow, messages, Service Broker or cursor statements (`IF`, `RAISERROR`, `PRINT`, `THROW`, `GOTO`, `ENABLE`/`DISABLE`, `RECEIVE`, `SEND` …) and a second top-level `SELECT` that `UNION`/`EXCEPT`/`INTERSECT` does not join; row locks (`FOR SHARE`, `FOR KEY SHARE`, `FOR NO KEY UPDATE`, SQL Server lock hints); functions with side effects (`pg_terminate_backend`, `pg_advisory_…`, `set_config`, `lo_export`, `dblink…`, `GET_LOCK`, `xp_…`) and functions that run SQL given as text (`query_to_xml` and the other `…_to_xml` functions, `ts_stat`, `crosstab`) – quoted names are checked too, without regard to case; executable MySQL comments `/*! … */` and optimizer hints `/*+ … */`; backslashes in literals (their meaning depends on server settings); unterminated literals or comments; and placeholders that do not match the parameters. Refusals carry a code and values, so the editor and the error answer show them translated. It refuses some harmless statements (a column named `update` must be quoted) and cannot see what a view or function called by the statement does – which is why layers 1 and 2 exist, and why the session is reset after each statement (below).

**Parameters are always bound**, never put into the text: the step's parameters are rendered as values and sent with the dialect's own placeholders (`$1` PostgreSQL, `?` MariaDB/MySQL, `@p1` SQL Server). Steward never builds SQL from values.

**Catalog queries.** Account, role, privilege, replication and table reads differ per DBMS, so Steward ships them (`server/src/dbms/catalog.ts`): a query step names `catalog: accounts | role-members | privileges | replication | tables | status` instead of SQL, and Steward runs the statement for the platform's DBMS (MariaDB and MySQL differ in their role tables and are told apart by the server version) and maps the rows to the same columns. One template therefore serves all three DBMS; the generated `REVOKE` statements (quoted per dialect) come with the rows. These statements are Steward's own, run in the same read-only transaction, and are kept reusable for schema snapshots (#222).

**Limits** are enforced on the server: a statement time limit (default 30 s, at most 300 s – `statement_timeout`, `MAX_EXECUTION_TIME`/`max_statement_time`, the request timeout, and a client-side timer), a row limit (default 1,000, at most 50,000) and a size limit (default 5 MB, at most 50 MB). The platform's values are ceilings a step can lower, not raise. Rows are read in batches; more than the limit fails the step unless it says `onLimit: truncate`, and then the result is marked truncated.

**Evidence.** The step records what was asked (platform, DBMS, the statement or catalog name with its SQL, the parameters – secret values masked) and stores the result like an HTTP answer (`columns`, `rows`, `rowCount`, `truncated`, `durationMs`), so run reports, evidence packs and later steps see it. Queries run in dry runs too (they are reads); test runs use recorded responses (`POST /sql/<step id>` on the platform) and never connect. Connection tests are audited as `platform.tested`.

**Outbound policy.** A database connection is a host:port connection, checked like Kafka and MQTT: with the policy _platforms_ the host and port of the platform's own settings are allowed (address safety still applies: no metadata or link-local addresses); with the policy _allow-list_ the host must be on the allow-list (`assertNetAllowed`). Sockets are opened by Steward with the guarded DNS lookup, so the address that was checked is the one connected to; TLS still verifies the host name. Under every policy, **Steward's own database** (the database of `SM_DATABASE_URL`) is refused (`DB_OWN_DATABASE`, `server/src/dbms/own.ts`): the same database name, the same port and an address in common, resolved like the guarded lookup, with every loopback, unspecified and local interface address counting as this machine; the check runs before connecting and again on the address the socket connects to. A database platform that reached Steward's own database would make designers' statements a path into the instance's data, even through a read-only account (the same reason the demo never reads it). Other databases on the same server stay allowed, so a small setup can keep its application databases in Steward's PostgreSQL cluster: a connection is bound to one database, PostgreSQL has no queries across databases, and `dblink` is refused by the statement check; the docs advise a role without `CONNECT` on Steward's database.

**Pooling: a small pool per platform**, not per step: at most `poolSize` connections (default 2, at most 5), closed after 60 s idle, closed at once when the platform's settings or credentials change or it is deleted (`invalidatePlatformCaches`), and on shutdown. A connection whose statement was cancelled, timed out or ended in an error the driver cannot recover from is destroyed, not returned. Per-step connections would make every for-each loop a connection storm; one shared connection would make one slow query block every run. What outlives a rollback is reset before a connection is reused: PostgreSQL runs Steward's own `SELECT pg_advisory_unlock_all()` after every statement (a failed reset destroys the connection) – `DISCARD ALL` would also work but resets nothing more that an accepted statement can change. A MariaDB/MySQL statement stopped by the client-side time limit or a cancel is ended with `KILL QUERY <connection id>` over a second, short-lived connection (same account, socket factory and outbound rules) before the connection is dropped; closing the socket alone leaves the server running it. **Driver errors** are masked with the platform's secrets (the redactor of the connection test) before they are stored or answered – run steps, monitor results, the MCP tool and the connection test.

**MCP gateway: off by default, read-only when on.** The gateway's tool `database_query` runs one statement through the same check, session rules and limits, audited like gateway calls. Changing calls stay refused for database platforms: `PUT …/mcp-gateway` with writes other than _off_ answers `MCP_WRITES_NOT_AVAILABLE`.

**Demo mode** uses a fake driver (`server/src/dbms/demo.ts`) for the host `postgres.demo.invalid`, answering the catalog queries and a few sample tables with canned rows. It never reads Steward's own database: a demo that reaches Steward's tables even with a dedicated role would make the demo platform a path into the instance's data.

## Not now (and how it would come)

- **Writes.** Always read-only in this step. A later manual step could run one approved statement with four-eyes (an approver other than the designer, the statement shown verbatim, its own control point in the assurance policy, a separate write account) – until then generated statements such as `REVOKE` are shown in a manual step and run by a person.
- **Oracle**, Entra ID tokens for SQL Server, IAM tokens for RDS; the table diagram (#222, step 2); data contracts (#221). Schema snapshots, their changes and the tbls import came in 0.8.0 (#222, step 1: catalog statements in `server/src/dbms/schema-catalog.ts`, run in the same read-only transaction; [DATABASES.md](../DATABASES.md#database-schemas)).

## Consequences

- One template serves every supported DBMS through the catalog queries; dialect-specific SQL lives in code with unit tests instead of in YAML.
- The statement check refuses some harmless statements; designers quote such identifiers or move logic into a view the read-only role may read.
- SQL Server's protection rests on the account and the rollback more than the other two. Revisit when SQL Server offers a read-only transaction or Steward gets a parser.
- Three new runtime dependencies (`mysql2`, `tedious` and its Azure sign-in libraries) are loaded only when a database platform is used. Integration tests for MariaDB and SQL Server run in CI with service containers; PostgreSQL is tested against a real cluster everywhere.
