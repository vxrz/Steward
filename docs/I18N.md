# Languages and translations

Steward's interface is available in **English** and **German**. English is the source of truth; every other language is a translation of the English texts and can be added without touching application code.

## How it works

| Part                | Where                                                         | Notes                                                                                                                                                                                                                  |
| ------------------- | ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Supported languages | `shared/src/locales.ts`                                       | The only list of languages. The web UI, the server's validation and the check script read it.                                                                                                                          |
| Web texts           | `web/src/locales/<lang>/<namespace>.json`                     | [i18next](https://www.i18next.com/) with `react-i18next`. One file per language and namespace (`common`, `nav`, `editor`, `runs`, …).                                                                                  |
| Web setup           | `web/src/i18n/`                                               | `index.ts` (initialisation, language switch, `formatLocale()`), `languages.ts` (namespace list), `resources.ts` + `i18next.d.ts` (type-safe keys), `meta.ts` (texts for step metadata), `errors.ts` (API error codes). |
| Server texts        | `server/src/i18n/locales/<lang>.json`                         | Notifications, e-mails, Teams cards and webhook messages. `t(locale, key, vars)` in `server/src/i18n/index.ts`.                                                                                                        |
| PDF reports         | `server/src/reports/i18n.ts`                                  | Own catalog (`REPORT_LANGS` in `shared/src/reports.ts`): reports are archived and hashed, so their wording changes deliberately.                                                                                       |
| Formatting          | `web/src/format.ts`, `web/src/components/dashboard/format.ts` | Dates, times, numbers, durations, bytes and relative times through `Intl`, with cached formatters.                                                                                                                     |

**Choosing the language.** On the first visit the browser language decides (`navigator.languages`, `de-AT` → `de`); anything unsupported falls back to English. The choice is stored in `localStorage` (`steward.language`) so the sign-in page already appears in it. People switch the language in the user menu, on their profile page, or on the sign-in page. Signed-in users' choice is saved on their account (`users.locale`, `PATCH /api/me { locale }`) and wins over the browser after the next sign-in, on any device. `null` means "no choice yet": the browser language applies in the UI and the **default language** (Settings → Language, `Settings.defaultLocale`) applies to server messages.

**Loading.** The English texts of the app shell (`common`, `nav`, `auth`, `errors`, `notifications`) are part of the first download. All other namespaces, and every namespace of other languages, are loaded on demand as small separate files (`import.meta.glob` in `web/src/i18n/index.ts`). A language switch loads the namespaces in use before switching, so the page does not flash a loader. `<html lang>` follows the UI language.

**Formatting.** Formatters use `formatLocale()`: the browser's regional variant when it matches the UI language (`de-AT`, `en-GB`), otherwise the language itself. So a British user with English UI gets `22/10/2026`, an American `10/22/2026`. Never use `toLocaleString()`, `toFixed()` or `String(n)` for numbers and dates people read; use the helpers in `web/src/format.ts` (`fmtDate`, `fmtDay`, `fmtNumber`, `fmtDuration`, `fmtBytes`, `listFormat`). Date and time inputs are the browser's own (`type="date"`, `datetime-local`); they follow `<html lang>` and the browser's regional settings. Steward has no Mantine date pickers (and so no dayjs locale to load).

**Server messages.** Each notification is rendered per recipient: in-app notifications and e-mails in the recipient's language (`users.locale`, falling back to the default language), Teams and webhook posts in the default language (a channel has many readers). Webhook payloads carry a `locale` field. In-app notifications are rendered when they are created; changing the language later does not re-translate old ones.

**PDF reports.** A report – a run report, a summary report or the PDF of a record – is generated in the language the request names (the dialogs preselect the UI language); without one, in the requesting user's profile language, otherwise English (`requestLang()` in `server/src/reports/service.ts`). Automatic reports use the language set in the process (Settings → PDF report), scheduled reports the language of the schedule. A report keeps its language for good: it is archived and its SHA-256 is in the audit log. The e-mail that delivers a scheduled report is written in each recipient's language, like every notification.

**Step metadata.** Step types, fields, ports and categories are described once in `shared/src/steps.ts` (English). The editor looks up their texts by id (`editor:steps.<type>.label`, `editor:steps.<type>.fields.<key>.help`, `editor:ports.<port>`, …) with the English text as `defaultValue` (`web/src/i18n/meta.ts`). A test (`server/test/i18n-sources.test.ts`) fails when the English JSON drifts from `shared`, so a new step or field cannot be forgotten.

**API errors.** Error responses keep an English `error` message and carry a stable `code` and its `params`. The UI shows `errors:codes.<CODE>` with the params filled in, and the server's message only for codes it does not know. See [Server errors](#server-errors). Validation issues of process definitions work the same way (`code` + `params` → `editor:validation.<code>`).

## Adding a language

French as an example:

1. Add a line to `shared/src/locales.ts`:
   ```ts
   { code: 'fr', nativeName: 'Français', englishName: 'French' },
   ```
   That is the only code change. The language menus, the default-language setting and the server's validation pick it up.
2. Copy `web/src/locales/en/` to `web/src/locales/fr/` and translate the values. Keep keys, `{{placeholders}}` and `<tags>` as they are. Add the plural forms the language needs (`_one`/`_many`/`_other` for French; `npm run i18n:check` lists missing forms).
3. Optional: copy `server/src/i18n/locales/en.json` to `fr.json`, translate it, and register it in `CATALOGS` in `server/src/i18n/index.ts` (`import fr from './locales/fr.json' with { type: 'json' };`). Without it, notifications for French users fall back to English.
4. Optional: PDF reports in French: add `'fr'` to `REPORT_LANGS` in `shared/src/reports.ts` and a `fr` catalog in `server/src/reports/i18n.ts` (TypeScript lists the missing texts). Until then reports for French users are generated in English, and the report dialogs offer the report languages only.
5. Run `npm run i18n:check` until it reports no problems, then `npm run typecheck` and `npm test`.

Missing keys fall back to English at runtime, so a partial translation never shows raw keys. In development (`npm run dev`) the console warns about keys that exist in no language: `[i18n] missing key "ns:key"`.

## Writing and changing texts

- **English first.** Add or change the text in `web/src/locales/en/…`; TypeScript then knows the key (`t('runs:status.failed')`), and typos fail `npm run typecheck`. Update the other languages in the same change, or at least run `npm run i18n:check` to see what is missing.
- **Namespaces** follow the pages: `processes`, `editor`, `runs`, `settings`, … Shared words (Save, Cancel, statuses, relative times) live in `common`. Use `useTranslation(['runs', 'common'])` and `t('common:save')` for keys from a second namespace.
- **Keys** describe the place, not the English text: `retention.notificationsHint`, not `deleteNotificationsAfterDays`. Group by section.
- **Whole sentences.** Never assemble a sentence from fragments (`t('run') + ' ' + t('failed')`): word order differs between languages. Use placeholders: `"upcomingLine": "{{process}} · {{date}} ({{relative}})"`.
- **Plurals** use i18next's suffixes and a numeric `count`: `"nRuns_one": "{{count}} run"`, `"nRuns_other": "{{count}} runs"`, `t('nRuns', { count })`. Do not write `run(s)`.
- **Markup in texts** goes through `<Trans>` with named components: `"step1": "Add a <a>platform</a> …"` with `components={{ a: <Anchor … /> }}`. Self-closing tags (`<path/>`) insert fixed content, for example code that contains angle brackets.
- **Literal `{{ … }}`** (JSONata examples) clashes with the placeholder syntax. Pass such text as a value: `"hint": "Expressions look like {{example}}"` with `{ example: '{{ vars.x }}' }`.
- **Numbers and dates** never go into the JSON preformatted; format them with the helpers in `web/src/format.ts` and pass the result as a value.
- **Enumerations** (statuses, roles, severities, widget types) are translated by value (`common:status.<value>`). Unknown values are shown as they are.

## Checking translations: `npm run i18n:check`

Compares every language with English, for the web namespaces and the server catalog, and reports missing keys, extra keys, empty texts, `{{placeholders}}` or `<tags>` that differ from English, missing plural forms (from `Intl.PluralRules`), declared languages without a folder and folders without a declaration.

```
npm run i18n:check              # human-readable; problems on stderr
npm run i18n:check -- --json    # machine-readable result on stdout
npm run i18n:check -- --help
```

Texts that are still the English ones are reported as `untranslated`. Words that are the same in both languages (_Name_, _Status_, _Dashboard_, _Monitor_, product names) are listed in `scripts/i18n-allow.json` under `sameAsEnglish.<lang>`. Placeholders, tags, URLs and ACRONYMS do not count as words, so `{{count}} PDF` passes without an entry.

Exit codes: `0` all languages in sync, `1` problems found, `2` usage or I/O error. CI runs it in the lint job.

## Finding hard-coded texts: `npm run i18n:literals`

Lists texts in `web/src` that a person sees but that do not go through `t()`: JSX text, text props (`title`, `label`, `placeholder`, `aria-label`, `description`, …), text properties in objects (`notifications.show({ title, message })`, `closeButtonProps: { 'aria-label': … }`), `data={['…']}` options and `notifyOk()`, `confirm()`. It reads the TypeScript syntax tree (no type checking) and runs in CI.

```
npm run i18n:literals              # findings on stderr: file:line:col, kind, text
npm run i18n:literals -- --json    # machine-readable
npm run i18n:literals -- web/src/pages/Records.tsx
```

Code-like strings (identifiers, CSS values, URLs, paths, `{{placeholders}}`, `$functions`, ACRONYMS) are not reported. For the rest:

- **Translate it** – the normal case.
- **Same in every language** (product names, units): add it to `scripts/i18n-allow.json` → `literals.exact`, or a pattern to `literals.patterns` (code examples such as `curl …`, header names).
- **Deliberately English** (English defaults that are translated by key, sample payloads): mark the line, the element or the statement with a comment and a reason: `// i18n-ignore: English defaults of editor:functions.<name>` or `{/* i18n-ignore: … */}`.

Texts in `t('key', { defaultValue: '…' })` are fallbacks and never reported.

## Server errors

Every error a person can see carries a code. On the server:

```ts
throw new HttpError(404, `Record ${id} not found`, 'RECORD_NOT_FOUND', { id });
```

The response is `{ "error": "Record CR-2026-0001 not found", "code": "RECORD_NOT_FOUND", "params": { "id": "CR-2026-0001" } }`. The English `error` stays for logs, the audit log and API clients. The web UI shows `errors:codes.RECORD_NOT_FOUND` (`"Dokument {{id}} nicht gefunden."`) through `errorText()` / `codeText()` in `web/src/i18n/errors.ts`:

- **Numbers** in params are formatted in the UI language; a numeric `count` selects the plural form (`<CODE>_one`, `<CODE>_other`).
- **`context`** picks a variant: `{ context: 'importRecords' }` shows `FORBIDDEN_importRecords` and falls back to `FORBIDDEN`. `require(perms, 'run', …)` sends `right_run`, so _FORBIDDEN_right_run_ says which right is missing.
- **Nested errors** (`errorParam(e)` → `{ message, code, params }`) are translated on their own: "Zeile 3: Monitor nicht gefunden."
- **Values the UI translates itself**: `statusParam(status)` (a record status, `records:status.<status>`), `fieldParam(typeKey, field)` (a field label, translated for the built-in types) and `RUN_STATUS`.
- **Lists** (arrays) are joined in the UI language: "Begründung, Risiko und Rückfallplan".

Reasons the server records with a result work the same way: a record action that is not allowed has `reason` (English) and `reasonCode` (`FOUR_EYES_AUTHOR`, `RECORD_APPROVERS_ONLY`, …), an imported file has `error`/`errorCode`/`errorParams` and `warnings`/`warningCodes`, a task the user may not decide has `cannotDecideReason`/`cannotDecideCode`. Zod schema errors become `INVALID_INPUT` ("Die Eingabe ist ungültig: …") with the English schema details inside.

`server/test/i18n-errors.test.ts` scans `server/src` with the TypeScript compiler: every `HttpError` in the records, services, credentials, reports, Gatus, MCP and monitor code must have a code, and every code thrown anywhere must have an English and a German text (and no text may be left over). Add the text to `web/src/locales/en/errors.json` and its translations when you add a code.

## Record types

Record types are data: an administrator can change the name, description, Markdown template, fields and select options of every type, including the built-in ones (CR, ADR, DR, SDR). Steward creates the built-in types once, in English (`DEFAULT_RECORD_TYPES` in `shared/src/records.ts`), and shows them translated **as long as a text is still the English default**:

| Text               | Where it is translated                                                                                                                                                                                                                                                                                                                |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Name               | `records:builtinTypes.<KEY>` (web), `BUILTIN_TEXTS` in `server/src/records/pdf-i18n.ts` (record PDF, records section of scheduled reports)                                                                                                                                                                                            |
| Description        | `records:builtin.types.<KEY>.description`                                                                                                                                                                                                                                                                                             |
| Template           | `records:builtin.types.<KEY>.template`: a new record starts with the template in the UI language. Records created through the API or MCP without a body get the template in the creator's profile language, else the default language (`recordTemplates.<KEY>` in the server catalog). The body is the record's content from then on. |
| Field labels, help | `records:builtin.fields.<field>.label` / `.help`, in forms, the record page, versions, error messages and the PDF                                                                                                                                                                                                                     |
| Select options     | `records:builtin.options.<field>.<value>`: the stored value stays `low`/`medium`/`high`; only the text shown changes                                                                                                                                                                                                                  |

A text an administrator changed is shown to everyone exactly as entered – in whatever language they wrote it. The type editor says so. This keeps one stored record type for all languages and keeps the stored values (and so the content hashes of frozen records) independent of the language. Tests keep the English JSON equal to `DEFAULT_RECORD_TYPES`, and the PDF and server texts equal to the web translations.

## What stays English, and why

| Stays English                                                                                                                                                               | Reason                                                                                                                                                                                                                    |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Audit log entries                                                                                                                                                           | The audit log is evidence. Its entries must read the same for every reader, auditor and export, and must not change meaning when someone switches the language. The column headings and filters around it are translated. |
| Run protocols, engine log lines, evidence (PDF/CSV/JSON reports)                                                                                                            | Same reason: they are stored records and are often handed to auditors or attached to tickets.                                                                                                                             |
| API error `message`s and server logs                                                                                                                                        | They are logged, audited and read by API clients. The UI translates the error `code`s instead ([Server errors](#server-errors)).                                                                                          |
| Schema validation messages from zod and the problems found in monitor definitions                                                                                           | Generic, rarely seen by people (API clients). The UI shows them inside a translated sentence ("Die Eingabe ist ungültig: …"); the important process-definition checks have codes and are translated.                      |
| Reasons and results recorded by the server (webhook rejections, a trigger's last result, schedule skips in the audit log, monitor check results and status-change messages) | Stored once, in English, like log lines; the UI labels around them are translated.                                                                                                                                        |
| User content                                                                                                                                                                | Process, platform, dashboard, schedule and team names, check names and messages, task texts, record and service texts, record types an administrator changed: whatever the author wrote.                                  |
| Connector specs (OpenAPI operation summaries, parameter descriptions)                                                                                                       | Come from the vendor's spec.                                                                                                                                                                                              |
| Web app manifest (PWA name/description)                                                                                                                                     | One static file per installation.                                                                                                                                                                                         |
