# Security and best-practice review, October 2026

This review looks at the whole application as it is now. Earlier reviews looked at one area each: the HTTP and sign-in surface, the process engine, crypto, audit and deployment, monitors, and the newer features (MCP, records, credentials, reports, Gatus). This one looks for what they could miss, mostly at the seams between features. It follows OWASP ASVS 4.0.3, level 2.

Every finding was checked with a proof-of-concept test or a precise code trace. The fixes come with regression tests in `server/test/security-review-2026-10.test.ts`, `server/test/session-config.test.ts` and `server/test/route-matrix.test.ts`. The first file also adds tests for critical paths that had none (see [Tests and coverage](#tests-and-coverage)).

## Summary

- **9 findings fixed** (3 Medium, 6 Low). There are no Critical or High findings.
- **Route matrix:** a permanent test calls all 322 routes with every role, without credentials, and with read-only and MCP tokens. It found one access-control gap (platform API specifications, Medium). Every other route matches the access model.
- **5 Low items accepted or left as proposals**, and 6 refactoring proposals.
- Dependencies: `npm audit --omit=dev` finds nothing. Two moderate advisories affect vitest (dev only).

## Findings

### F1 – Platform API specifications visible without a permission on the platform (Medium, fixed)

`GET /api/platforms/:id/specs`, `GET /api/platforms/:id/operations` and `GET /api/specs/:specId/content` had no permission check. The platform itself (`GET /api/platforms/:id`) answers 404 to users without a permission on it, and the comment above the platform list says names, base URLs and docs are hidden from them.

- **Exploit:** a viewer, approver or auditor, or an operator outside a platform's access list, lists the specifications and operations of any platform. That shows its endpoints and spec ids, and with a spec id the full OpenAPI document with server URLs and examples. It also confirms that a platform id exists.
- **Verified:** the route matrix (approver, auditor and viewer got 200), then `security-review-2026-10.test.ts › platform API specifications`.
- **Fix:** all three routes require some permission on the platform (`routes/index.ts`, `platforms.specPlatformId`). The MCP gateway already checked `use`.

### F2 – API tokens could manage identities, sign-in and the vault (Medium, fixed)

`POST /api/me/tokens` refuses API tokens, so a token cannot create new tokens. But a full-access token of an administrator could still call `POST /api/users` (a new administrator with a known password), `POST /api/users/:id/reset-password` (a one-time password for any local account), `PUT /api/sso/providers/:id`, `PUT /api/settings` (password sign-in, outbound policy) and `POST /api/vault/passphrase`.

- **Exploit:** a token leaks from a script or CI job. The attacker creates an administrator account, signs in and creates new tokens. Revoking the leaked token no longer helps.
- **Verified:** PoC in the route matrix: `POST /api/users` with an administrator's full token gave 200.
- **Fix:** `SESSION_ONLY_ROUTES` in `app.ts` – these routes answer `403 SESSION_REQUIRED` to any API token: users, teams, single sign-on providers, `PUT /api/settings`, the master passphrase, vault lock and token creation. Reading stays possible.

### F3 – Memory exhaustion through single sign-on starts (Medium, fixed)

`GET /api/auth/oidc/:id/start` is public. Each call stored a pending sign-in (state, PKCE verifier, return path) for 10 minutes, with no upper bound. The return path could be as long as the request line.

- **Exploit:** an anonymous client loops over the start URL with an 8 KB `returnTo`. 3000 requests grew the heap by about 200 MB; a sustained flood exhausts the memory. This needs an enabled provider, whose id `/api/auth/status` shows.
- **Verified:** PoC test (heap growth measured), then `security-review-2026-10.test.ts › single sign-on start`.
- **Fix:** at most 5000 pending sign-ins (the oldest is dropped), return paths over 1 KB fall back to `/`. A flood can still make a real user's sign-in in progress fail (they start again); a per-address limit would be the next step.

### F4 – Session lifetime and cookie prefix (Low, fixed)

ASVS 4.0.3 V3.3.2 (level 2) asks for re-authentication after 12 hours, or 30 minutes of inactivity. Steward used a 12-hour idle timeout and 7 days absolute. V3.4.4 asks for the `__Host-` prefix.

- **Fix:** `SM_SESSION_IDLE_MINUTES` (default 30) and `SM_SESSION_MAX_HOURS` (default 12). The idle extension never goes past the absolute lifetime, and the cookie's `Max-Age` follows it. Over HTTPS (built-in TLS or an `https://` `SM_PUBLIC_URL`) the cookie is called `__Host-sm_session`. An open Steward tab polls notifications every 30 s, so it stays signed in; a hidden tab does not. Everyone signs in again once after the update.
- **Tests:** `session-config.test.ts`.

### F5 – Guessing the current password through "change password" (Low, fixed)

`POST /api/auth/password` checks the current password, but it was not rate-limited or audited. With a stolen session (no password), the attacker could guess the password behind it at the speed of scrypt.

- **Fix:** at most 5 wrong current passwords per account in 15 minutes (then 429), each one audited as `user.password_change_failed`.

### F6 – Webhook mapping preview (Low, fixed)

`POST /api/triggers/preview-mapping` evaluates JSONata expressions. It was open to every signed-in user, also viewers and auditors, and took any number of expressions (up to the 25 MB body limit), each with a 1-second limit.

- **Fix:** only for users who may run at least one process (who could set up a trigger). At most 100 mapped inputs (also for saved triggers) and 5 s for all expressions together.

### F7 – Query strings without validation (Low, fixed)

Many routes read `req.query` without a schema. Fastify turns repeated parameters into arrays.

- **Exploit / effect:** `/api/runs?limit=abc` and `/api/audit?limit=abc` answered 500 with the SQLite message (`datatype mismatch`; PostgreSQL messages are more detailed). `/api/tasks?status=a&status=b`, `/api/bundle/export?processes=a&processes=b`, `/api/runs/:id/report.pdf?lang=a&lang=b`, the monitor history and results and the dataset metrics also gave 500. `/api/runs?limit=-1` returned all runs at once.
- **Fix:** zod schemas for the query strings of runs, audit, tasks, process versions, process scope, dataset metrics, bundle export, reports, report schedules, trigger fires, monitor history and results, and notifications. The error handler no longer returns the message of a database error; it returns the request id, and the details go to the log.

### F8 – Body fields without size limits (Low, fixed)

The global body limit is 25 MB. Some fields had no own limit: user name, display name, e-mail and password when an administrator creates a user; team names and members; platform fields and ad-hoc request paths and headers; schedule fields; the comment of a task decision (it ends up in the run protocol and the audit log, which can never be cleaned); process and dashboard text (parsed as YAML). They now have limits. Process and dashboard text: 2 MB (`MAX_DEFINITION_TEXT`).

### F9 – No warnings for risky settings (Low, fixed)

`securityWarnings()` in `config.ts` is logged at startup. It warns when Steward is reachable under another host name without HTTPS, when demo mode runs on a network address, when the master passphrase comes from `SM_MASTER_PASSPHRASE` instead of a file, when metrics are public, and when sessions are longer than ASVS level 2.

### Accepted items

- **A3 – connector types.** Connector types are reusable templates that an administrator makes on purpose. `GET /api/platform-presets` and the export show their base URL, settings and docs to every signed-in user, also when the source platform has an access list. Keep this in mind before you make a type from a restricted platform. If this becomes a problem: hide `baseUrl`, `config` and `docs` of custom types from users who cannot create platforms, and make the export admin-only.
- **A4 – e-mail domains.** Only administrators set the recipients of audit checkpoint e-mails and notification test e-mails. They are not checked against the allowed domains. A checkpoint holds hashes only.
- **A5 – tokens after a password change.** API tokens stay valid when a password is changed or reset (like personal access tokens elsewhere). After an account compromise, revoke the tokens under _Settings → API tokens_ (all users' tokens). Deactivating the account stops them at once.

## Route permission matrix

`server/test/route-matrix.test.ts` reads the route table from Fastify (`registeredRoutes(app)` in `app.ts`, collected by an `onRoute` hook) and checks it against an explicit table. Each of the 322 routes (48 of them under `/api/v1`) is classified:

| Class                                                   | Routes |
| ------------------------------------------------------- | ------ |
| Every signed-in role                                    | 127    |
| Administrators only                                     | 84     |
| Roles that run processes (admin, designer, operator)    | 25     |
| Public (health, sign-in, theme, OpenAPI document, …)    | 22     |
| Roles that design (admin, designer)                     | 19     |
| Administrators and auditors                             | 15     |
| Roles that use platforms by default                     | 12     |
| Machine endpoints with their own secret (webhooks, MCP) | 8      |
| Everyone but read-only accounts / everyone but viewers  | 10     |

The test checks:

1. Every registered route is in the table, and every table entry is a route. **A new route fails the test until it is classified.**
2. Roles outside a route's list never get a 2xx (nor a 5xx). Changing routes get a valid body, so a refusal is a permission decision and not a validation error. Changing routes are only sent where they must be refused, to keep the fixtures intact.
3. Roles in a route's list get a 2xx or 3xx for GET routes (so the table is not vacuous).
4. Without credentials every non-public route answers 401.
5. A read-only token is refused on every changing route; an MCP token on every route outside `/api/mcp`.
6. The session-only routes (F2) refuse a full-access token.

Results: the first run found F1 (and F2 through check 6). All other differences between the first guess and the code were intended rules (for example, designers edit monitors by default, operators maintain credentials register entries and records, auditors see all report schedules). They are written down in the table now.

`SM_ROUTE_MATRIX_OBSERVE=<file>` also sends the changing requests of allowed roles and writes every "route role status" line – a starting point for classifying new routes.

Limits: the matrix uses objects without access lists, owned by the administrator. Access lists and owners are covered by the feature tests (`rbac.test.ts`, `records-security.test.ts`, `credentials.test.ts`, `monitors.test.ts`, …).

## Refactoring proposals

- **P1 – step-up authentication for sensitive actions** (ASVS 3.7.1). Ask for the password again (local accounts) or a fresh sign-in with `max_age` (single sign-on) before creating API tokens, changing roles, resetting passwords and changing sign-in settings. Needs a small server API (`POST /api/auth/confirm` → a short-lived "recently authenticated" mark on the session) and a dialog in the web UI. With the 12-hour session limit (F4) the gap is smaller.
- **P2 – passwords:** drop the composition rule (letters plus digit or symbol) and check new passwords against a bundled list of the most common breached passwords (ASVS 2.1.7, 2.1.9).
- **P3 – one place for route permission helpers.** `me()` is defined in 11 files (with and without the `NOT_SIGNED_IN` code), `params()` in 14, `requireProcess`/`requireRun`/`requireRunView`/`requireBindingsUsable` in 4 route files with slightly different rules (`engine-extras.ts` accepts any of several rights, `triggers.ts` does not hide platforms with 404). Move them to `auth/permissions.ts` (or `routes/guards.ts`) so a fix applies everywhere.
- **P4 – declare access on the route.** Many routes parse the body before the permission check, so an unauthorised user sees validation messages (and uploads go into memory before a refusal). A route option such as `config: { access: 'admin' }` checked in the preHandler – and read by the route matrix – would make the check come first and the table self-documenting. The same mechanism could replace `SESSION_ONLY_ROUTES`.
- **P5 – smaller default body limit.** The global body limit is 25 MB for every signed-in request. A 1 MB default with explicit larger limits on the upload and import routes would bound memory per request.
- **P6 – shared helpers for duplicated logic.** Two CSV writers with formula escaping (`audit-export.ts`, `credentials/service.ts`), four "shorten for display" helpers, three e-mail address checks (regex in `users.ts`, regex in `audit-anchor.ts`, zod in report schedules) and four e-mail paths (notifications with the domain rules, report schedules, credential reminders through notifications, audit checkpoints directly). The link systems are already consistent: records and services share `records/links.ts` with one resolver per kind, and credentials' "used by" links come in as backlinks with the register's read rules.
- **Long functions in security-relevant code:** `v1Routes` (817 lines), `registerRoutes` (781), `buildApp` (201, with the auth hook), `execBrowser` (184), `execHttp` (138). Splitting the route registration by area (as `ops.ts`, `reports.ts` and others already are) would make reviews easier.

## Backup and restore

[INSTALL.md](INSTALL.md) describes backups (database dump plus data directory; with SQLite, a copy of the data directory while Steward is stopped). Keep in mind: a backup has to contain the database **and** the data folder (vault file, artifacts, documents, reports, the audit anchor file), and the master passphrase is needed to restore. A restored older backup shows up as a broken audit chain against newer checkpoints (that is the purpose of the signed checkpoints) – keep the checkpoint e-mails or SIEM log lines to explain it.
