# Insights Hub users and memberships

The example processes that change Insights Hub accounts – **11 Access review 2** (removing memberships), **13 Offboard leavers**, **17 Add users to several groups** and **18 Deactivate or reactivate users** (0.27.0) – call the Identity Management API v3 (`/api/identitymanagement/v3`, SCIM users and groups; the path comes from the platform variable `idmPath`). This page says what they rely on and where that comes from – checked against the Insights Hub documentation and the published OpenAPI specification (version 3.3), and, where those say nothing, against the UAA service Insights Hub uses – so you can check it against your tenant.

## How the examples handle what is not documented

- **A refused removal** – a default group, or one your tenant protects for another reason – is not guessed: #11 and #13 send one request per group, keep every answer (status and message, Insights Hub's `errors[].message` or UAA's `error_description`) and report it per user and group; the other removals go on, and a check (_Every deletion or removal went through_, in #11 _Every membership removal went through_) lists the failures. Add such a group to the input _Never remove_ and it is left alone from then on. `404` counts as _not a member (any more)_.
- **The default groups** are left out by name (input _Never remove_, by default `openid`, `profile`, `email`, `phone`, `address`, `roles`, `user_attributes`, `uaa.user`, `uaa.offline_token`, `approvals.me`, `password.write`, `scim.me`, `oauth.approvals` – the UAA defaults and the OIDC standard scopes) and `INDIRECT` memberships by their type; the approval shows what will be removed and what is kept.
- **Deactivation** sends the account as it was read – `userName`, `name`, `emails` as the user name (the specification's rule) and `subtenants` of a subtenant user – with only `active` changed, then reads the account again: _deactivated_ or _reactivated_ only when `active` really changed, otherwise _request accepted, but active is …_ or _failed_ with the API's message. Try it on a test account first.
- **Evidence**: each process keeps the memberships as they were in the approval (four-eyes for 11, 13 and 18), the report and the documented access change (_rights before_; for 18 the reason _Account deactivated (memberships kept)_).

## The demo

The simulated tenant lists `openid`, `profile` and `email` as DIRECT memberships of the leaver _Karla Lang_ (only of her, so the other examples keep their figures) and refuses to remove them with `400` and an Insights Hub error object (an assumption, see above); deleting her account succeeds with them. `PUT /Users/{id}` requires `userName`, `name` and `emails`, refuses another user name or an e-mail address other than the user name, and sets `active`.
